Como escolher

No JD Edwards EnterpriseOne existem várias formas de integração. A escolha depende principalmente de três coisas: se a interface é em tempo real ou em lote, se o JDE envia ou recebe os dados, e qual versão do Tools Release você usa. [7] [15]

Por trás das três perguntas há um princípio que vale para todas as opções: as regras de negócio do JDE moram nas aplicações e nas business functions, não no banco de dados. Toda integração que grava dados precisa passar por essa camada. O que muda de uma opção para outra é a porta de entrada, o protocolo e a latência.

  1. Latência. Tempo real significa uma transação por chamada, com resposta em segundos, quase sempre síncrona. Lote significa volumes grandes processados em janelas, com a possibilidade de corrigir e reprocessar o que falhou.
  2. Direção. Entrada é quando o JDE recebe dados (um pedido criado por um portal). Saída é quando o JDE envia ou avisa (um pedido aprovado que precisa chegar ao armazém). Algumas opções servem aos dois sentidos.
  3. Tools Release. É a versão da base técnica do JDE, independente da versão das aplicações (9.2). O Orchestrator existe no Tools 9.2 e ganha recursos a cada atualização; ambientes em Tools antigos dependem de Business Services ou de conectores. [5]

Para gestores: o custo de uma integração raramente está no método escolhido; está no tratamento de erros e na operação do dia a dia. Para qualquer interface, pergunte: quem vê o erro, quem corrige e como se reprocessa?

Glossário mínimo

AIS Server
Application Interface Services: servidor que expõe o JDE como serviços REST com JSON.
Orchestrator
Motor que roda no AIS Server e executa orquestrações, sequências de passos desenhadas no Orchestrator Studio.
Tools Release
Versão da camada técnica do JDE (runtime, servidores, ferramentas), atualizada separadamente das aplicações.
UBE
Universal Batch Engine: programa em lote (relatório ou processo), identificado por um R, como R09110Z.
BSFN
Business function: função reutilizável em C ou em NER (Named Event Rules, gerada em C).
MBF
Master business function: BSFN que encapsula uma transação inteira, como o pedido de venda.
Z-file
Tabela de interoperabilidade (interface table) usada como área de espera para lotes.
OMW e UDO
Object Management Workbench controla objetos de desenvolvimento; UDOs (user defined objects) são objetos criados por usuários, como orquestrações.
JDENET
Protocolo interno de comunicação entre os servidores do JDE.
CNC
Configurable Network Computing: a administração técnica do JDE (servidores, pacotes, segurança).

Onde cada opção se encaixa

Uma instalação do JDE tem vários servidores, e cada opção de integração conversa com um deles. O Enterprise Server executa as business functions e os UBEs. O HTML Server (JAS) executa as aplicações web. O AIS Server, o Business Services Server e o Transaction Server são servidores Java em WebLogic (ou WebSphere, em alguns casos), instalados e administrados pelo Server Manager. [4]

Para o arquiteto de infraestrutura, cada servidor adicional é uma instância a dimensionar, atualizar, monitorar e proteger. As versões suportadas de WebLogic, Java, sistema operacional e banco são definidas pela matriz de certificações da Oracle para o Tools Release em uso.

Em uma frase: o Orchestrator transforma processos do JDE em APIs REST, montadas visualmente, que respeitam as mesmas regras das telas.

Explicação conceitual e técnica

O AIS Server é um servidor de serviços REST que, configurado junto com o HTML Server, dá acesso a formulários e dados do EnterpriseOne por JSON sobre HTTP. [3] O Orchestrator usa o AIS Server como base e processa as orquestrações salvas nele para transformar dados externos em processos de negócio no JDE. [1]

Conceitualmente, ele é uma fachada de API: quem chama não precisa saber qual tela, versão ou business function usar. Chama um endpoint com nome de negócio, como CriarPedidoVenda, e a orquestração cuida do resto. Isso separa o contrato da integração da implementação dentro do JDE.

Tecnicamente, uma orquestração é uma sequência de passos chamados service requests: [2]

  • Form request: executa uma aplicação interativa como um usuário faria, preenchendo campos e apertando botões. As event rules e validações da tela rodam normalmente.
  • Data request: consulta tabelas ou business views, com filtros e agregações.
  • Business function e report: chama uma BSFN diretamente ou dispara um UBE.
  • Custom: executa lógica própria em Groovy ou Java.
  • Connector: dá acesso seguro a recursos externos, como um serviço REST, um banco de dados ou uma orquestração de outro sistema JDE. [5]
  • Message: envia e-mail ou mensagem para o Work Center.

Regras (condições), cross-references e white lists traduzem códigos e decidem o caminho. As notificações avaliam dados do JDE ou de serviços REST externos para detectar situações que pedem atenção, e o agendador embutido executa orquestrações e notificações periodicamente. [5] [6] Desde o Tools 9.2.4, o Orchestrator Studio é instalado junto com o AIS Server e acessado pela própria URL dele. [1]

A grande vantagem é que as regras de negócio das telas do JDE são respeitadas: um form request sobre o P4210 passa pelas mesmas validações, versões e opções de processamento que um usuário digitando o pedido.

Quando é útil

  • Portais e e-commerce que criam pedidos, consultam preço, saldo ou status em tempo real.
  • iPaaS (Oracle Integration, MuleSoft, Boomi) conectando o JDE a SaaS como CRM, WMS ou transportadoras.

Em uma frase: os dados entram numa sala de espera, e um programa padrão do JDE os valida e grava como se alguém tivesse digitado.

Explicação conceitual e técnica

As Z-files são o método clássico para cargas em lote. Cada uma é uma interface table com as colunas da tabela de aplicação e mais campos de controle. O nome segue a tabela de origem com o sufixo Z1: a F4211 tem a F4211Z1. Quando a tabela de interface passaria de 250 colunas, cria-se uma tabela adicional com uma letra depois do sufixo, como F4211Z1A. [8]

Os campos de controle formam a chave e o estado de cada registro: usuário (EDUS), lote (EDBT), número da transação (EDTN), linha (EDLN), indicador de processado (EDSP), ação (EDTC: A para incluir, C para alterar, D para excluir) e tipo de transação (EDTR). [7]

Na entrada, um sistema externo grava na Z-file e depois roda o UBE processador, por exemplo o R09110Z para lançamentos contábeis ou o R4211Z1I para pedidos de venda. O processador lê os registros ainda não processados, chama a master business function com a versão definida nas opções de processamento e grava nas tabelas definitivas. Os registros com erro ficam na Z-file, a mensagem vai para o Work Center, e é possível corrigi-los e reprocessá-los. [7]

Também funciona como saída: as opções de processamento da aplicação ou os controles de exportação (P0047) fazem o JDE gravar cada transação na Z-file, com o código de ação, para um sistema externo ler. [9] É robusto e aproveita a validação padrão, mas não é tempo real.

Em uma frase: web services SOAP escritos em Java que embrulham business functions do JDE.

Explicação conceitual e técnica

Business Services são classes Java desenvolvidas no JDeveloper, controladas no OMW como qualquer objeto do JDE e publicadas como web services num Business Services Server em WebLogic ou WebSphere. [10] [11]

Um published business service é um objeto do OMW que representa uma classe Java que publica várias operações. [10] Ele delega a business services internos, que trabalham com value objects e chamam business functions e acessos a dados pela API de tempo de execução do JDE. A Oracle entrega vários serviços prontos (clientes, fornecedores, itens, pedidos, estoque), e você pode criar os seus.

O caminho inverso também existe: o JDE pode ser consumidor de web services. Uma business function chama um business service consumidor, que chama o serviço externo e devolve a resposta à lógica do JDE.

Ainda é bastante usado, mas vem perdendo espaço para o AIS e o Orchestrator: SOAP é mais pesado, e cada mudança exige ciclo de desenvolvimento Java, build de pacote e deploy no servidor, enquanto uma orquestração se ajusta no Studio.

Em uma frase: o JDE avisa os sistemas interessados no instante em que um negócio acontece, sem que eles precisem perguntar.

Explicação conceitual e técnica

Um real-time event é uma notificação de saída para um sistema terceiro de que uma transação de negócio ocorreu no JDE. [12] O modelo é publicar e assinar: o JDE publica o evento uma vez, e cada assinante recebe a sua cópia.

Tecnicamente, as business functions das transações geram o evento em XML (por exemplo, RTSOOUT para pedidos de venda). Os kernels de eventos do Enterprise Server passam o evento ao Transaction Server, que usa filas e tópicos JMS para garantir a entrega e roteia a informação para as filas de cada assinante com assinatura ativa. [12] Os transportes incluem JMS, MQ Series e conectores, e os assinantes são cadastrados no P90702A. [14]

Há três famílias de eventos: Z events, gerados a partir das Z-files de saída; real-time events, gerados pelas business functions no momento da transação; e XAPI, em que o JDE envia uma requisição e espera a resposta do sistema externo. [13] O destino pode ser uma fila JMS ou MQ, um web service via BSSV ou o Orchestrator, e nos Tools recentes as notificações do Orchestrator são uma alternativa mais simples para muitos casos.

Em uma frase: quando o outro lado só fala por arquivo, um programa em lote do JDE lê ou escreve esse arquivo no layout combinado.

Explicação conceitual e técnica

UBEs customizados e Table Conversions servem para leitura ou gravação de arquivos texto ou CSV, geração de flat files e conversões entre tabelas. Um UBE pode ler um arquivo, chamar as business functions de edição e gravar os dados. [15] [23] [24]

A Table Conversion é um tipo de programa em lote feito para mover e transformar dados: de tabela para tabela, de arquivo para tabela ou de tabela para arquivo, com mapeamento de colunas e event rules. O UBE escrito no Report Design Aid dá mais controle: lê o arquivo linha a linha, interpreta registros de cabeçalho, detalhe e trailer, chama business functions e gera um relatório de conferência.

Um padrão robusto é combinar as opções: o UBE ou a Table Conversion apenas converte o arquivo para a Z-file, e o processador padrão faz a validação e a gravação. Assim a regra de negócio continua com a Oracle, e o código customizado fica só com o layout.

É comum em interfaces bancárias (no Brasil, os layouts CNAB de remessa e retorno) e em arquivos fiscais ou de parceiros que não usam EDI.

Em uma frase: é a própria lógica de negócio do JDE; as outras opções são maneiras de chegar até ela.

Explicação conceitual e técnica

Business functions podem ser escritas em C ou em NER (Named Event Rules, que o JDE converte em C). As master business functions encapsulam uma transação inteira e seguem um ciclo: BeginDoc valida o cabeçalho e abre o cache, EditLine valida cada linha, EditDoc confere o documento e EndDoc obtém os next numbers e grava tudo. Para pedidos de venda, a família é F4211FSBeginDoc, F4211FSEditLine, F4211FSEditDoc e F4211FSEndDoc. [21] [22]

Até o EndDoc, os dados ficam no cache do JDE, o que permite validar o documento inteiro antes de gravar. O artigo Cache no JD Edwards explica esse mecanismo em detalhe. [20]

Normalmente as BSFNs são acionadas a partir de um UBE, do BSSV ou do Orchestrator, e não isoladamente por um sistema externo: elas precisam de um contexto de execução do JDE (usuário, ambiente, transação), que o programa hospedeiro fornece.

Em uma frase: troca de documentos comerciais padronizados com clientes e fornecedores, com o JDE validando cada documento antes de ele virar pedido ou fatura.

Explicação conceitual e técnica

O módulo Data Interface for Electronic Data Interchange (sistema 47) é a interface entre os dados do JDE e o software tradutor. [17] O tradutor, externo ao JDE, converte as mensagens padronizadas (X12, EDIFACT) em arquivos planos e vice-versa; o JDE lê e grava as tabelas F47xxx.

Na entrada de um pedido do cliente (850), o tradutor grava o cabeçalho na F47011 e as linhas na F47012; o R47011 lê essas tabelas, valida e cria o pedido de venda nas F4201 e F4211. [18] Como as F47 são uma área de espera, é possível inspecionar e corrigir os dados antes de eles virarem um pedido real. Na saída, o R47042 extrai as faturas para as tabelas de saída (F47046 e F47047), que o tradutor converte em 810.

O EDI é indicado para troca de documentos padronizados com clientes e fornecedores, geralmente junto com um tradutor EDI e um canal de comunicação (VAN ou AS2).

Em uma frase: ler direto do banco é aceitável para relatórios; gravar direto é pedir para ter dados inconsistentes.

Explicação conceitual e técnica

Gravar direto no banco é tecnicamente possível, mas é desaconselhado. Um INSERT ou UPDATE ignora tudo o que a aplicação faz: validações contra o dicionário de dados e as UDCs, next numbers (F0002), tabelas relacionadas (compromissos de estoque na F41021, saldos contábeis na F0902), campos de auditoria (usuário, programa, data e hora), workflow e a segurança do JDE. O resultado costuma ser saldo que não fecha, número duplicado e registro órfão. A exceção é a própria Z-file, que foi feita para receber dados de fora.

Para leitura (relatórios, BI, views), é aceitável, desde que se respeitem as convenções do JDE:

  • Datas julianas no formato CYYDDD: 126271 é o dia 271 de 2026, 28/09/2026.
  • Decimais implícitos: valores são gravados como inteiros, com as casas definidas no dicionário de dados ou pela moeda. [25]
  • UDCs: códigos precisam ser traduzidos pela F0005.
  • Campos alinhados: a filial (MCU) tem 12 posições alinhadas à direita.
  • A segurança por linha e por coluna do JDE não se aplica a quem lê o banco.

Segurança em todas as opções

  • Identidade: um usuário de serviço por integração, sem acesso interativo, com role mínima no Security Workbench; credenciais em cofre, nunca em scripts ou XML. [27]
  • Transporte: TLS em tudo (AIS, BSSV, Transaction Server, SFTP, AS2); o JDENET fica restrito à rede dos servidores.
  • Perímetro: API gateway ou proxy reverso, WAF, limite de requisições e lista de origens; servidores do JDE em zona interna.
  • Dados: mínimo de dados pessoais em Z-files e arquivos, purge periódico, criptografia de arquivos em repouso e mascaramento em réplicas, em linha com a LGPD.
  • Auditoria: campos de auditoria do JDE preenchidos com o usuário da integração, logs correlacionados e registro de quem aprovou cada orquestração.

Governança

  • Catálogo de interfaces: dono de negócio, dono técnico, método, volume, SLA e procedimento de erro de cada integração.
  • Fila de erros com responsável: Work Center, rejeitados de UBE e filas mortas precisam de alguém que olhe todo dia.
  • Regressão: cada atualização de Tools, ESU ou versão pode mudar uma regra; as integrações entram no plano de testes.
  • Custo total: além de licenças e servidores, conte as pessoas que operam e corrigem as interfaces.

Resumo

Para integrações novas e em tempo real, use o Orchestrator/AIS. Para volumes grandes em lote, as Z-files com os processadores padrão são o caminho mais seguro. Para avisar sistemas externos sobre eventos, use o RTE ou as notificações do Orchestrator.

Para fixar

  • As regras de negócio estão nas aplicações e business functions; toda gravação deve passar por elas.
  • Orchestrator: API REST montada no Studio, com as regras das telas.
  • Z-files: área de espera + processador padrão; erros ficam para corrigir e reprocessar.
  • BSSV e conectores legados: manter o que existe e planejar a migração.
  • RTE: o JDE avisa; os assinantes precisam ser idempotentes.
  • UBE e EDI: arquivos e documentos padronizados, com transferência segura.
  • SQL: ler sim, gravar não.

Revisão rápida

1. Quais são as três perguntas que definem o método de integração?

Se é tempo real ou lote, se o JDE envia ou recebe os dados, e qual Tools Release está em uso.

2. Por que o Orchestrator respeita as regras de negócio?

Porque os form requests executam as aplicações como um usuário, com as mesmas event rules, versões e opções de processamento.

3. O que acontece com um registro de Z-file que falha na validação?

Ele continua na Z-file, a mensagem vai para o Work Center, e o registro pode ser corrigido e reprocessado.

4. Qual opção usar para avisar um WMS de que um pedido foi liberado?

Real-Time Events (ou uma notificação do Orchestrator), com o WMS assinando o evento de pedido.

5. Por que um sistema externo não chama uma business function diretamente?

Porque ela precisa de um contexto de execução do JDE; quem fornece esse contexto é o hospedeiro: UBE, BSSV ou Orchestrator.

6. Quando o SQL direto é aceitável?

Só para leitura, de preferência em réplica e com usuário somente leitura, convertendo datas julianas, decimais e UDCs.

How to choose

JD Edwards EnterpriseOne offers several ways to integrate. The choice depends mainly on three things: whether the interface is real time or batch, whether JDE sends or receives the data, and which Tools Release you run. [7] [15]

Behind those three questions sits a principle that applies to every option: JDE business rules live in the applications and in the business functions, not in the database. Every integration that writes data must go through that layer. What changes from one option to another is the entry point, the protocol and the latency.

  1. Latency. Real time means one transaction per call, with an answer in seconds, almost always synchronous. Batch means large volumes processed in windows, with the ability to fix and reprocess what failed.
  2. Direction. Inbound is when JDE receives data (an order created by a portal). Outbound is when JDE sends or notifies (an approved order that must reach the warehouse). Some options serve both directions.
  3. Tools Release. This is the version of the JDE technical foundation, independent of the application release (9.2). The Orchestrator exists in Tools 9.2 and gains features with every update; environments on older Tools depend on Business Services or connectors. [5]

For managers: the cost of an integration rarely lies in the chosen method; it lies in error handling and day-to-day operation. For any interface, ask: who sees the error, who fixes it and how is it reprocessed?

Where each option fits

A JDE installation has several servers, and each integration option talks to one of them. The Enterprise Server runs business functions and UBEs. The HTML Server (JAS) runs the web applications. The AIS Server, the Business Services Server and the Transaction Server are Java servers on WebLogic (or WebSphere, in some cases), installed and managed with Server Manager. [4]

For the infrastructure architect, each additional server is an instance to size, patch, monitor and protect. The supported versions of WebLogic, Java, operating system and database are defined by Oracle's certification matrix for the Tools Release in use.

Conceptual and technical explanation

The AIS Server is a REST services server that, configured with the HTML Server, gives access to EnterpriseOne forms and data through JSON over HTTP. [3] The Orchestrator uses the AIS Server as its foundation and processes the orchestrations saved there to turn external data into business processes in JDE. [1]

Conceptually, it is an API façade: the caller does not need to know which screen, version or business function to use. It calls an endpoint with a business name, such as CreateSalesOrder, and the orchestration handles the rest. This separates the integration contract from the implementation inside JDE.

Technically, an orchestration is a sequence of steps called service requests: [2]

  • Form request: runs an interactive application as a user would, filling in fields and pressing buttons. The screen's event rules and validations run as usual.
  • Data request: queries tables or business views, with filters and aggregations.
  • Business function and report: calls a BSFN directly or launches a UBE.
  • Custom: runs your own logic in Groovy or Java.
  • Connector: gives secure access to external resources, such as a REST service, a database or an orchestration on another JDE system. [5]
  • Message: sends an email or a Work Center message.

Rules (conditions), cross-references and white lists translate codes and decide the path. Notifications assess JDE data or external REST services to detect conditions that need attention, and the built-in scheduler runs orchestrations and notifications periodically. [5] [6] Since Tools 9.2.4, the Orchestrator Studio is deployed together with the AIS Server and reached through its own URL. [1]

The big advantage is that the business rules of the JDE screens are honoured: a form request on P4210 goes through the same validations, versions and processing options as a user keying the order.

Z-files (interoperability tables)

Direction
Inbound and outbound
Latency
Batch (minutes to hours)
Protocol
Table + processor UBE
Oracle's position
Standard for batches

In one sentence: data enters a waiting room, and a standard JDE program validates and saves it as if someone had keyed it in.

Conceptual and technical explanation

Z-files are the classic method for batch loads. Each is an interface table with the columns of the application table plus control fields. The name follows the source table with the Z1 suffix: F4211 has F4211Z1. When the interface table would exceed 250 columns, an additional table is created with a letter after the suffix, such as F4211Z1A. [8]

The control fields form the key and the state of each record: user (EDUS), batch (EDBT), transaction number (EDTN), line (EDLN), processed flag (EDSP), action (EDTC: A to add, C to change, D to delete) and transaction type (EDTR). [7]

Inbound, an external system writes to the Z-file and then runs the processor UBE, for example R09110Z for journal entries or R4211Z1I for sales orders. The processor reads the unprocessed records, calls the master business function with the version set in the processing options and writes to the final tables. Records in error stay in the Z-file, the message goes to the Work Center, and they can be fixed and reprocessed. [7]

It also works outbound: the application's processing options or the data export controls (P0047) make JDE write each transaction to the Z-file, with its action code, for an external system to read. [9] It is robust and reuses the standard validation, but it is not real time.

In one sentence: SOAP web services written in Java that wrap JDE business functions.

Conceptual and technical explanation

Business Services are Java classes developed in JDeveloper, controlled in OMW like any other JDE object and published as web services on a Business Services Server running WebLogic or WebSphere. [10] [11]

A published business service is an OMW object that represents one Java class publishing several operations. It is still widely used, but it is losing ground to AIS and the Orchestrator: SOAP is heavier, and each change requires a Java development cycle, a package build and a deployment to the server, while an orchestration is adjusted in the Studio.

Real-Time Events (RTE)

Direction
Outbound
Latency
Real time, asynchronous
Protocol
XML over JMS, MQ or HTTP
Oracle's position
Supported

In one sentence: JDE tells interested systems the moment something happens in the business, without them having to ask.

Conceptual and technical explanation

A real-time event is an outbound notification to a third-party system that a business transaction has occurred in JDE. [12] The model is publish and subscribe: JDE publishes the event once, and each subscriber receives its own copy.

Technically, the transaction business functions raise the event in XML (for example, RTSOOUT for sales orders). The Enterprise Server event kernels pass the event to the Transaction Server, which uses JMS queues and topics to guarantee delivery and routes the information to the queues of each subscriber with an active subscription. [12] Transports include JMS, MQ Series and connectors, and subscribers are registered in P90702A. [14]

There are three families of events: Z events, produced from the outbound Z-files; real-time events, raised by business functions at transaction time; and XAPI, where JDE sends a request and waits for the external system's reply. [13] The target can be a JMS or MQ queue, a web service through BSSV or the Orchestrator, and on recent Tools the Orchestrator notifications are a simpler alternative for many cases.

OperationsWebLogic consoleAlerts on queue depth, age of the oldest message and delivery failures

  • CRM, WMS or e-commerce must know at once that an order was created, changed or invoiced.
  • Synchronising master data (customers, suppliers, items) with an MDM.
  • Feeding a data lake or a streaming platform with the transactions.
  • Triggering external workflows without polling the database.

Custom UBEs and Table Conversions

Direction
Inbound and outbound
Latency

Protocol

Oracle's position

In one sentence: when the other side only speaks through files, a JDE batch program reads or writes that file in the agreed layout.

Conceptual and technical explanation

Custom UBEs and Table Conversions are used to read or write text or CSV files, produce flat files and convert between tables. A UBE can read a file, call the edit business functions and write the data. [15] [23] [24]

A Table Conversion is a kind of batch program built to move and transform data: table to table, file to table or table to file, with column mapping and event rules. A UBE written in Report Design Aid gives more control: it reads the file line by line, interprets header, detail and trailer records, calls business functions and prints an audit report.

A robust pattern combines the options: the UBE or Table Conversion only converts the file into the Z-file, and the standard processor does the validation and the write. The business rule stays with Oracle, and the custom code only deals with the layout.

It is common in bank interfaces (in Brazil, the CNAB remittance and return layouts) and in tax files or files from partners that do not use EDI.

Direction
Mainly inbound
Latency
Depends on the caller
Protocol
Internal JDE call
Oracle's position

In one sentence: this is JDE's business logic itself; the other options are ways of reaching it.

Conceptual and technical explanation

Business functions can be written in C or in NER (Named Event Rules, which JDE converts into C). Master business functions wrap a whole transaction and follow a cycle: BeginDoc validates the header and opens the cache, EditLine validates each line, EditDoc checks the document and EndDoc gets the next numbers and writes everything. For sales orders, the family is F4211FSBeginDoc, F4211FSEditLine, F4211FSEditDoc and F4211FSEndDoc. [21] [22]

Until EndDoc, the data stays in the JDE cache, which allows the whole document to be validated before anything is written. The article Caching in JD Edwards explains this mechanism in detail. [20]

BSFNs are normally triggered from a UBE, BSSV or the Orchestrator, not called on their own by an external system: they need a JDE execution context (user, environment, transaction), which the host program provides.

In one sentence: exchanging standardised business documents with customers and suppliers, with JDE validating each document before it becomes an order or invoice.

Conceptual and technical explanation

The Data Interface for Electronic Data Interchange module (system 47) is the interface between JDE data and the translator software. [17] The translator, outside JDE, turns standard messages (X12, EDIFACT) into flat files and back; JDE reads and writes the F47xxx tables.

EDI is the right fit for exchanging standardised documents with customers and suppliers, usually with an EDI translator and a communication channel (VAN or AS2).

Direct database access (SQL)

Direction
Read
Latency
Immediate
Protocol
SQL / JDBC / ODBC
Position
Read yes, write no

In one sentence: reading straight from the database is acceptable for reporting; writing straight to it is asking for inconsistent data.

Conceptual and technical explanation

Writing directly to the database is technically possible, but it is discouraged. An INSERT or UPDATE skips everything the application does: edits against the data dictionary and UDCs, next numbers (F0002), related tables (inventory commitments in F41021, account balances in F0902), audit fields (user, program, date and time), workflow and JDE security. The usual result is balances that do not tie, duplicate numbers and orphan records. The exception is the Z-file itself, which was designed to receive data from outside.

For reading (reports, BI, views) it is acceptable, as long as JDE conventions are respected:

  • Julian dates in CYYDDD format: 126271 is day 271 of 2026, 28/09/2026.
  • Implied decimals: values are stored as integers, with the decimal places defined in the data dictionary or by the currency. [25]
  • UDCs: codes must be translated through F0005.
  • Justified fields: the business unit (MCU) has 12 right-justified positions.
  • JDE row and column security does not apply to whoever reads the database.

ModelDirect queries on the tablesA semantic layer that converts dates, decimals and UDCs once; incremental loads by the last-update date fields

Required knowledge

SQL, the JDE data model (tables, business views, data dictionary), Julian dates, implied decimals and UDCs; on the DBA side, replicas and permissions. For reporting inside JDE itself, One View Reporting is an alternative that respects system security. [26]

  • Data warehouse, data lake and BI dashboards.

  • One-off checks and audits.

Security across all options

  • Identity: one service user per integration, with no interactive access and a least-privilege role in Security Workbench; credentials in a vault, never in scripts or XML. [27]
  • Transport: TLS everywhere (AIS, BSSV, Transaction Server, SFTP, AS2); JDENET stays within the server network.
  • Perimeter: API gateway or reverse proxy, WAF, rate limiting and a list of allowed sources; JDE servers in an internal zone.
  • Data: as little personal data as possible in Z-files and files, periodic purge, encryption of files at rest and masking in replicas, in line with GDPR and LGPD.
  • Audit: JDE audit fields filled with the integration user, correlated logs and a record of who approved each orchestration.

Governance

  • Interface catalogue: business owner, technical owner, method, volume, SLA and error procedure for each integration.
  • Error queue with an owner: Work Center, UBE rejects and dead-letter queues need someone to look at them every day.
  • Regression: every Tools update, ESU or version change can alter a rule; integrations belong in the test plan.
  • Total cost: besides licences and servers, count the people who run and fix the interfaces.

Summary

For new, real-time integrations, use the Orchestrator/AIS. For large batch volumes, Z-files with the standard processors are the safest path. To notify external systems about events, use RTE or Orchestrator notifications.

Key points

  • Business rules live in applications and business functions; every write must go through them.
  • Orchestrator: a REST API built in the Studio, with the screens' rules.
  • Z-files: staging area + standard processor; errors stay to be fixed and reprocessed.
  • BSSV and legacy connectors: keep what exists and plan the migration.
  • RTE: JDE notifies; subscribers must be idempotent.
  • UBE and EDI: files and standardised documents, with secure transfer.
  • SQL: read yes, write no.

Quick review

1. Which three questions define the integration method?

Whether it is real time or batch, whether JDE sends or receives the data, and which Tools Release is in use.

2. Why does the Orchestrator honour the business rules?

Because form requests run the applications as a user would, with the same event rules, versions and processing options.

3. What happens to a Z-file record that fails validation?

It stays in the Z-file, the message goes to the Work Center, and the record can be fixed and reprocessed.

4. Which option notifies a WMS that an order was released?

Real-Time Events (or an Orchestrator notification), with the WMS subscribing to the order event.

5. Why does an external system not call a business function directly?

Because it needs a JDE execution context, which the host provides: a UBE, BSSV or the Orchestrator.

6. When is direct SQL acceptable?

Only for reading, preferably on a replica and with a read-only user, converting Julian dates, decimals and UDCs.

Come scegliere

JD Edwards EnterpriseOne offre diverse forme di integrazione. La scelta dipende soprattutto da tre cose: se l'interfaccia è in tempo reale o batch, se JDE invia o riceve i dati e quale Tools Release si usa. [7] [15]

Dietro le tre domande c'è un principio che vale per tutte le opzioni: le regole di business di JDE stanno nelle applicazioni e nelle business function, non nel database. Ogni integrazione che scrive dati deve passare da quello strato. Da un'opzione all'altra cambiano il punto di ingresso, il protocollo e la latenza.

  1. Latenza. Tempo reale significa una transazione per chiamata, con risposta in pochi secondi, quasi sempre sincrona. Batch significa grandi volumi elaborati in finestre, con la possibilità di correggere e rielaborare ciò che è fallito.
  2. Direzione. Ingresso è quando JDE riceve dati (un ordine creato da un portale). Uscita è quando JDE invia o avvisa (un ordine approvato che deve arrivare al magazzino). Alcune opzioni servono entrambe le direzioni.
  3. Tools Release. È la versione della base tecnica di JDE, indipendente dalla release delle applicazioni (9.2). L'Orchestrator esiste nel Tools 9.2 e si arricchisce a ogni aggiornamento; gli ambienti con Tools datati dipendono dai Business Services o dai connettori. [5]

Per i manager: il costo di un'integrazione raramente sta nel metodo scelto; sta nella gestione degli errori e nell'operatività quotidiana. Per ogni interfaccia chiedete: chi vede l'errore, chi lo corregge e come si rielabora?

Dove si colloca ogni opzione

Un'installazione di JDE ha diversi server, e ogni opzione di integrazione dialoga con uno di essi. L'Enterprise Server esegue le business function e gli UBE. L'HTML Server (JAS) esegue le applicazioni web. L'AIS Server, il Business Services Server e il Transaction Server sono server Java su WebLogic (o WebSphere, in alcuni casi), installati e amministrati con il Server Manager. [4]

Per l'architetto infrastrutturale, ogni server in più è un'istanza da dimensionare, aggiornare, monitorare e proteggere. Le versioni supportate di WebLogic, Java, sistema operativo e database sono definite dalla matrice di certificazione di Oracle per il Tools Release in uso.

In una frase: l'Orchestrator trasforma i processi di JDE in API REST, costruite visivamente, che rispettano le stesse regole delle videate.

Spiegazione concettuale e tecnica

L'AIS Server è un server di servizi REST che, configurato insieme all'HTML Server, dà accesso a form e dati di EnterpriseOne tramite JSON su HTTP. [3] L'Orchestrator usa l'AIS Server come base ed elabora le orchestrazioni salvate lì per trasformare dati esterni in processi di business in JDE. [1]

Concettualmente è una facciata di API: chi chiama non deve sapere quale videata, versione o business function usare. Chiama un endpoint con un nome di business, come CreaOrdineVendita, e l'orchestrazione fa il resto. Così il contratto dell'integrazione resta separato dall'implementazione dentro JDE.

Tecnicamente, un'orchestrazione è una sequenza di passi chiamati service request: [2]

  • Form request: esegue un'applicazione interattiva come farebbe un utente, compilando campi e premendo pulsanti. Le event rule e le validazioni della videata girano normalmente.
  • Data request: interroga tabelle o business view, con filtri e aggregazioni.
  • Business function e report: chiama direttamente una BSFN o avvia un UBE.
  • Custom: esegue logica propria in Groovy o Java.
  • Connettore: dà accesso sicuro a risorse esterne, come un servizio REST, un database o un'orchestrazione di un altro sistema JDE. [5]
  • Messaggio: invia un'e-mail o un messaggio al Work Center.

Regole (condizioni), cross-reference e white list traducono i codici e decidono il percorso. Le notifiche valutano dati di JDE o di servizi REST esterni per individuare situazioni che richiedono attenzione, e lo scheduler integrato esegue orchestrazioni e notifiche periodicamente. [5] [6] Dal Tools 9.2.4 l'Orchestrator Studio viene installato insieme all'AIS Server e si raggiunge dal suo stesso URL. [1]

Il grande vantaggio è che le regole di business delle videate di JDE vengono rispettate: un form request sul P4210 passa per le stesse validazioni, versioni e opzioni di elaborazione di un utente che digita l'ordine.

In una frase: i dati entrano in una sala d'attesa, e un programma standard di JDE li valida e li registra come se qualcuno li avesse digitati.

Spiegazione concettuale e tecnica

Le Z-file sono il metodo classico per i caricamenti batch. Ognuna è una interface table con le colonne della tabella applicativa più alcuni campi di controllo. Il nome segue la tabella d'origine con il suffisso Z1: la F4211 ha la F4211Z1. Quando la tabella di interfaccia supererebbe le 250 colonne, si crea una tabella aggiuntiva con una lettera dopo il suffisso, come F4211Z1A. [8]

I campi di controllo formano la chiave e lo stato di ogni record: utente (EDUS), batch (EDBT), numero di transazione (EDTN), riga (EDLN), indicatore di elaborato (EDSP), azione (EDTC: A per aggiungere, C per modificare, D per eliminare) e tipo di transazione (EDTR). [7]

In ingresso, un sistema esterno scrive nella Z-file e poi lancia l'UBE elaboratore, per esempio l'R09110Z per le registrazioni contabili o l'R4211Z1I per gli ordini di vendita. L'elaboratore legge i record non ancora elaborati, chiama la master business function con la versione definita nelle opzioni di elaborazione e scrive nelle tabelle definitive. I record in errore restano nella Z-file, il messaggio va nel Work Center e si possono correggere e rielaborare. [7]

Funziona anche in uscita: le opzioni di elaborazione dell'applicazione o i controlli di esportazione (P0047) fanno sì che JDE scriva ogni transazione nella Z-file, con il codice azione, perché un sistema esterno la legga. [9] È robusto e sfrutta la validazione standard, ma non è in tempo reale.

Spiegazione concettuale e tecnica

I Business Services sono classi Java sviluppate in JDeveloper, gestite in OMW come ogni altro oggetto di JDE e pubblicate come web service su un Business Services Server in WebLogic o WebSphere. [10] [11]

Un published business service è un oggetto OMW che rappresenta una classe Java che pubblica più operazioni. [10] Delega a business service interni, che lavorano con value object e chiamano business function e accessi ai dati tramite l'API di runtime di JDE. Esiste anche il percorso inverso: JDE può essere consumatore di web service. Una business function chiama un business service consumatore, che chiama il servizio esterno e restituisce la risposta alla logica di JDE.

È ancora molto usato, ma sta perdendo terreno rispetto ad AIS e Orchestrator: SOAP è più pesante, e ogni modifica richiede un ciclo di sviluppo Java, la build del pacchetto e il deploy sul server, mentre un'orchestrazione si adatta nello Studio.

In una frase: JDE avvisa i sistemi interessati nell'istante in cui succede qualcosa nel business, senza che debbano chiederlo.

Spiegazione concettuale e tecnica

Un real-time event è una notifica in uscita verso un sistema terzo che una transazione di business è avvenuta in JDE. [12] Il modello è publish e subscribe: JDE pubblica l'evento una volta e ogni sottoscrittore riceve la propria copia.

Tecnicamente, le business function delle transazioni generano l'evento in XML (per esempio RTSOOUT per gli ordini di vendita). I kernel degli eventi dell'Enterprise Server passano l'evento al Transaction Server, che usa code e topic JMS per garantire la consegna e instrada l'informazione verso le code di ogni sottoscrittore con una sottoscrizione attiva. [12] I trasporti includono JMS, MQ Series e connettori, e i sottoscrittori si registrano nel P90702A. [14]

Ci sono tre famiglie di eventi: gli Z event, prodotti a partire dalle Z-file in uscita; i real-time event, generati dalle business function al momento della transazione; e gli XAPI, in cui JDE invia una richiesta e attende la risposta del sistema esterno. [13] La destinazione può essere una coda JMS o MQ, un web service tramite BSSV o l'Orchestrator, e nei Tools recenti le notifiche dell'Orchestrator sono un'alternativa più semplice in molti casi.

In una frase: quando l'altra parte parla solo tramite file, un programma batch di JDE legge o scrive quel file nel tracciato concordato.

Spiegazione concettuale e tecnica

UBE personalizzati e Table Conversion servono a leggere o scrivere file di testo o CSV, a generare flat file e a convertire dati tra tabelle. Un UBE può leggere un file, chiamare le business function di validazione e scrivere i dati. [15] [23] [24]

La Table Conversion è un tipo di programma batch fatto per spostare e trasformare dati: da tabella a tabella, da file a tabella o da tabella a file, con mappatura delle colonne ed event rule. Un UBE scritto con il Report Design Aid dà più controllo: legge il file riga per riga, interpreta record di testata, dettaglio e coda, chiama business function e stampa un report di controllo.

Un pattern robusto combina le opzioni: l'UBE o la Table Conversion si limita a convertire il file nella Z-file, e l'elaboratore standard fa la validazione e la scrittura. Così la regola di business resta a Oracle e il codice personalizzato si occupa solo del tracciato.

È comune nelle interfacce bancarie (in Brasile, i tracciati CNAB di invio e ritorno; in Italia, i flussi CBI) e nei file fiscali o di partner che non usano l'EDI.

In una frase: è la logica di business di JDE stessa; le altre opzioni sono modi per arrivarci.

Spiegazione concettuale e tecnica

Le business function si possono scrivere in C o in NER (Named Event Rules, che JDE converte in C). Le master business function incapsulano un'intera transazione e seguono un ciclo: BeginDoc valida la testata e apre la cache, EditLine valida ogni riga, EditDoc controlla il documento ed EndDoc ottiene i next number e scrive tutto. Per gli ordini di vendita la famiglia è F4211FSBeginDoc, F4211FSEditLine, F4211FSEditDoc e F4211FSEndDoc. [21] [22]

Fino all'EndDoc i dati restano nella cache di JDE, il che permette di validare l'intero documento prima di scrivere. L'articolo La cache in JD Edwards spiega questo meccanismo nel dettaglio. [20]

Di norma le BSFN vengono avviate da un UBE, dal BSSV o dall'Orchestrator, e non chiamate isolatamente da un sistema esterno: hanno bisogno di un contesto di esecuzione di JDE (utente, ambiente, transazione), fornito dal programma ospite.

In una frase: scambio di documenti commerciali standardizzati con clienti e fornitori, con JDE che valida ogni documento prima che diventi un ordine o una fattura.

Spiegazione concettuale e tecnica

Il modulo Data Interface for Electronic Data Interchange (sistema 47) è l'interfaccia tra i dati di JDE e il software di traduzione. [17] Il traduttore, esterno a JDE, converte i messaggi standard (X12, EDIFACT) in file piatti e viceversa; JDE legge e scrive le tabelle F47xxx.

Per un ordine del cliente in ingresso (850), il traduttore scrive la testata nella F47011 e le righe nella F47012; l'R47011 legge queste tabelle, le valida e crea l'ordine di vendita nelle F4201 e F4211. [18] Poiché le F47 sono un'area di sosta, i dati si possono ispezionare e correggere prima che diventino un ordine reale. In uscita, l'R47042 estrae le fatture nelle tabelle di uscita (F47046 e F47047), che il traduttore converte in 810.

L'EDI è indicato per lo scambio di documenti standardizzati con clienti e fornitori, di solito insieme a un traduttore EDI e a un canale di comunicazione (VAN o AS2).

I connettori legacy comprendono: [16] [15]

In una frase: leggere direttamente dal database è accettabile per i report; scriverci direttamente significa cercarsi dati incoerenti.

Spiegazione concettuale e tecnica

Scrivere direttamente nel database è tecnicamente possibile, ma è sconsigliato. Un INSERT o un UPDATE salta tutto ciò che fa l'applicazione: validazioni sul dizionario dati e sulle UDC, next number (F0002), tabelle correlate (impegni di magazzino nella F41021, saldi contabili nella F0902), campi di audit (utente, programma, data e ora), workflow e sicurezza di JDE. Il risultato tipico sono saldi che non quadrano, numeri duplicati e record orfani. L'eccezione è la Z-file stessa, progettata per ricevere dati dall'esterno.

In lettura (report, BI, viste) è accettabile, purché si rispettino le convenzioni di JDE:

  • Date giuliane nel formato CYYDDD: 126271 è il giorno 271 del 2026, il 28/09/2026.
  • Decimali impliciti: i valori sono salvati come interi, con i decimali definiti nel dizionario dati o dalla valuta. [25]
  • UDC: i codici vanno tradotti tramite la F0005.
  • Campi allineati: la business unit (MCU) ha 12 posizioni allineate a destra.
  • La sicurezza per riga e per colonna di JDE non si applica a chi legge il database.

Architettura minima e consigliata

AspettoMinimaConsigliata

ModelloQuery dirette sulle tabelleUno strato semantico che converte date, decimali e UDC una sola volta; caricamenti incrementali sui campi di data di aggiornamento

SQL, modello dati di JDE (tabelle, business view, dizionario dati), date giuliane, decimali impliciti e UDC; lato DBA, repliche e permessi. Per la reportistica dentro JDE, One View Reporting è un'alternativa che rispetta la sicurezza del sistema. [26]

Quando è utile

  • Data warehouse, data lake e cruscotti di BI.
  • Interrogazioni analitiche pesanti che non devono girare dentro JDE.
  • Verifiche e audit puntuali.

Sicurezza in tutte le opzioni

  • Identità: un utente di servizio per integrazione, senza accesso interattivo e con ruolo minimo nel Security Workbench; credenziali in un vault, mai in script o XML. [27]
  • Trasporto: TLS ovunque (AIS, BSSV, Transaction Server, SFTP, AS2); JDENET resta nella rete dei server.
  • Perimetro: API gateway o reverse proxy, WAF, limiti di richieste e lista delle origini ammesse; server di JDE in una zona interna.
  • Dati: il minimo di dati personali in Z-file e file, purge periodico, cifratura dei file a riposo e mascheramento nelle repliche, in linea con il GDPR.
  • Audit: campi di audit di JDE valorizzati con l'utente dell'integrazione, log correlati e traccia di chi ha approvato ogni orchestrazione.

Governance

  • Catalogo delle interfacce: responsabile di business, responsabile tecnico, metodo, volume, SLA e procedura di errore di ogni integrazione.
  • Coda degli errori con un responsabile: Work Center, scarti degli UBE e code dei messaggi non consegnati richiedono qualcuno che li guardi ogni giorno.
  • Regressione: ogni aggiornamento di Tools, ESU o versione può cambiare una regola; le integrazioni fanno parte del piano di test.
  • Costo totale: oltre a licenze e server, contate le persone che gestiscono e correggono le interfacce.

Riepilogo

Per integrazioni nuove e in tempo reale, usate l'Orchestrator/AIS. Per grandi volumi in batch, le Z-file con gli elaboratori standard sono la strada più sicura. Per avvisare i sistemi esterni degli eventi, usate gli RTE o le notifiche dell'Orchestrator.

Da ricordare

  • Le regole di business stanno nelle applicazioni e nelle business function; ogni scrittura deve passare da lì.
  • Orchestrator: un'API REST costruita nello Studio, con le regole delle videate.
  • Z-file: area di sosta + elaboratore standard; gli errori restano da correggere e rielaborare.
  • BSSV e connettori legacy: mantenere l'esistente e pianificare la migrazione.
  • RTE: JDE avvisa; i sottoscrittori devono essere idempotenti.
  • UBE ed EDI: file e documenti standardizzati, con trasferimento sicuro.
  • SQL: leggere sì, scrivere no.

Ripasso veloce

1. Quali sono le tre domande che definiscono il metodo di integrazione?

Se è in tempo reale o batch, se JDE invia o riceve i dati e quale Tools Release è in uso.

2. Perché l'Orchestrator rispetta le regole di business?

Perché i form request eseguono le applicazioni come un utente, con le stesse event rule, versioni e opzioni di elaborazione.

3. Cosa succede a un record di Z-file che non supera la validazione?

Resta nella Z-file, il messaggio va nel Work Center e il record si può correggere e rielaborare.

4. Quale opzione usare per avvisare un WMS che un ordine è stato rilasciato?

I Real-Time Events (o una notifica dell'Orchestrator), con il WMS sottoscritto all'evento dell'ordine.

5. Perché un sistema esterno non chiama direttamente una business function?

Perché serve un contesto di esecuzione di JDE, fornito dall'ospite: un UBE, il BSSV o l'Orchestrator.

6. Quando è accettabile l'SQL diretto?

Solo in lettura, preferibilmente su una replica e con un utente in sola lettura, convertendo date giuliane, decimali e UDC.

Cómo elegir

JD Edwards EnterpriseOne ofrece varias formas de integración. La elección depende sobre todo de tres cosas: si la interfaz es en tiempo real o batch, si JDE envía o recibe los datos y qué Tools Release se usa. [7] [15]

Detrás de las tres preguntas hay un principio que vale para todas las opciones: las reglas de negocio de JDE están en las aplicaciones y en las business functions, no en la base de datos. Toda integración que escribe datos debe pasar por esa capa. De una opción a otra cambian el punto de entrada, el protocolo y la latencia.

  1. Latencia. Tiempo real significa una transacción por llamada, con respuesta en pocos segundos, casi siempre síncrona. Batch significa grandes volúmenes procesados en ventanas, con la posibilidad de corregir y reprocesar lo que falló.
  2. Dirección. Entrada es cuando JDE recibe datos (un pedido creado desde un portal). Salida es cuando JDE envía o avisa (un pedido aprobado que debe llegar al almacén). Algunas opciones sirven para ambas direcciones.
  3. Tools Release. Es la versión de la base técnica de JDE, independiente de la release de las aplicaciones (9.2). El Orchestrator existe en Tools 9.2 y se enriquece con cada actualización; los entornos con Tools antiguos dependen de los Business Services o de los conectores. [5]

Para gerentes: el costo de una integración rara vez está en el método elegido; está en el manejo de errores y en la operación diaria. Para cada interfaz pregunten: ¿quién ve el error, quién lo corrige y cómo se reprocesa?

Dónde encaja cada opción

Una instalación de JDE tiene varios servidores, y cada opción de integración conversa con uno de ellos. El Enterprise Server ejecuta las business functions y los UBE. El HTML Server (JAS) ejecuta las aplicaciones web. El AIS Server, el Business Services Server y el Transaction Server son servidores Java sobre WebLogic (o WebSphere, en algunos casos), instalados y administrados con el Server Manager. [4]

Para el arquitecto de infraestructura, cada servidor adicional es una instancia que dimensionar, actualizar, monitorear y proteger. Las versiones soportadas de WebLogic, Java, sistema operativo y base de datos las define la matriz de certificación de Oracle para el Tools Release en uso.

En una frase: el Orchestrator convierte los procesos de JDE en API REST, construidas visualmente, que respetan las mismas reglas que las pantallas.

Explicación conceptual y técnica

El AIS Server es un servidor de servicios REST que, configurado junto con el HTML Server, da acceso a formularios y datos de EnterpriseOne mediante JSON sobre HTTP. [3] El Orchestrator usa el AIS Server como base y procesa las orquestaciones guardadas allí para transformar datos externos en procesos de negocio en JDE. [1]

Conceptualmente es una fachada de API: quien llama no necesita saber qué pantalla, versión o business function usar. Llama a un endpoint con un nombre de negocio, como CrearPedidoVenta, y la orquestación hace el resto. Así el contrato de la integración queda separado de la implementación dentro de JDE.

Técnicamente, una orquestación es una secuencia de pasos llamados service requests: [2]

  • Form request: ejecuta una aplicación interactiva como lo haría un usuario, llenando campos y presionando botones. Las event rules y las validaciones de la pantalla corren normalmente.
  • Data request: consulta tablas o business views, con filtros y agregaciones.
  • Business function e informe: llama directamente a una BSFN o lanza un UBE.
  • Custom: ejecuta lógica propia en Groovy o Java.
  • Conector: da acceso seguro a recursos externos, como un servicio REST, una base de datos o una orquestación de otro sistema JDE. [5]
  • Mensaje: envía un correo electrónico o un mensaje al Work Center.

Reglas (condiciones), referencias cruzadas y listas blancas traducen los códigos y deciden el camino. Las notificaciones evalúan datos de JDE o de servicios REST externos para detectar situaciones que requieren atención, y el scheduler integrado ejecuta orquestaciones y notificaciones periódicamente. [5] [6] Desde Tools 9.2.4 el Orchestrator Studio se instala junto con el AIS Server y se accede desde su misma URL. [1]

La gran ventaja es que se respetan las reglas de negocio de las pantallas de JDE: un form request sobre el P4210 pasa por las mismas validaciones, versiones y opciones de proceso que un usuario que digita el pedido.

En una frase: los datos entran en una sala de espera, y un programa estándar de JDE los valida y los registra como si alguien los hubiera digitado.

Explicación conceptual y técnica

Las tablas Z son el método clásico para las cargas batch. Cada una es una interface table con las columnas de la tabla de la aplicación más algunos campos de control. El nombre sigue a la tabla de origen con el sufijo Z1: la F4211 tiene la F4211Z1. Cuando la tabla de interfaz superaría las 250 columnas, se crea una tabla adicional con una letra después del sufijo, como F4211Z1A. [8]

Los campos de control forman la clave y el estado de cada registro: usuario (EDUS), batch (EDBT), número de transacción (EDTN), línea (EDLN), indicador de procesado (EDSP), acción (EDTC: A para agregar, C para cambiar, D para eliminar) y tipo de transacción (EDTR). [7]

En la entrada, un sistema externo escribe en la tabla Z y luego lanza el UBE procesador, por ejemplo el R09110Z para los asientos contables o el R4211Z1I para los pedidos de venta. El procesador lee los registros aún no procesados, llama a la master business function con la versión definida en las opciones de proceso y escribe en las tablas definitivas. Los registros con error quedan en la tabla Z, el mensaje va al Work Center y se pueden corregir y reprocesar. [7]

También funciona en la salida: las opciones de proceso de la aplicación o los controles de exportación (P0047) hacen que JDE escriba cada transacción en la tabla Z, con el código de acción, para que un sistema externo la lea. [9] Es robusto y aprovecha la validación estándar, pero no es en tiempo real.

Explicación conceptual y técnica

Los Business Services son clases Java desarrolladas en JDeveloper, gestionadas en OMW como cualquier otro objeto de JDE y publicadas como web services en un Business Services Server sobre WebLogic o WebSphere. [10] [11]

En una frase: JDE avisa a los sistemas interesados en el instante en que algo sucede en el negocio, sin que tengan que preguntar.

Explicación conceptual y técnica

Un real-time event es una notificación saliente hacia un sistema de terceros de que una transacción de negocio ocurrió en JDE. [12] El modelo es publish y subscribe: JDE publica el evento una vez y cada suscriptor recibe su propia copia.

Técnicamente, las business functions de las transacciones generan el evento en XML (por ejemplo RTSOOUT para los pedidos de venta). Los kernels de eventos del Enterprise Server pasan el evento al Transaction Server, que usa colas y tópicos JMS para garantizar la entrega y enruta la información hacia las colas de cada suscriptor con una suscripción activa. [12] Los transportes incluyen JMS, MQ Series y conectores, y los suscriptores se registran en el P90702A. [14]

Hay tres familias de eventos: los Z events, producidos a partir de las tablas Z de salida; los real-time events, generados por las business functions en el momento de la transacción; y los XAPI, en los que JDE envía una solicitud y espera la respuesta del sistema externo. [13] El destino puede ser una cola JMS o MQ, un web service mediante BSSV o el Orchestrator, y en los Tools recientes las notificaciones del Orchestrator son una alternativa más sencilla en muchos casos.

En una frase: cuando la otra parte solo habla mediante archivos, un programa batch de JDE lee o escribe ese archivo en el formato acordado.

Explicación conceptual y técnica

Los UBE personalizados y la Table Conversion sirven para leer o escribir archivos de texto o CSV, generar flat files y convertir datos entre tablas. Un UBE puede leer un archivo, llamar a las business functions de validación y escribir los datos. [15] [23] [24]

La Table Conversion es un tipo de programa batch hecho para mover y transformar datos: de tabla a tabla, de archivo a tabla o de tabla a archivo, con mapeo de columnas y event rules. Un UBE escrito con el Report Design Aid da más control: lee el archivo línea por línea, interpreta registros de cabecera, detalle y cola, llama a business functions e imprime un informe de control.

Un patrón robusto combina las opciones: el UBE o la Table Conversion se limita a convertir el archivo a la tabla Z, y el procesador estándar hace la validación y la escritura. Así la regla de negocio queda en manos de Oracle y el código personalizado se ocupa solo del formato.

Es común en las interfaces bancarias (en Brasil, los formatos CNAB de envío y retorno; en España, las normas del Cuaderno de la AEB y los ficheros SEPA) y en los archivos fiscales o de socios que no usan EDI.

Explicación conceptual y técnica

En una frase: intercambio de documentos comerciales estandarizados con clientes y proveedores, con JDE validando cada documento antes de que se convierta en un pedido o una factura.

Explicación conceptual y técnica

El módulo Data Interface for Electronic Data Interchange (sistema 47) es la interfaz entre los datos de JDE y el software de traducción. [17] El traductor, externo a JDE, convierte los mensajes estándar (X12, EDIFACT) en archivos planos y viceversa; JDE lee y escribe las tablas F47xxx.

Para un pedido de cliente de entrada (850), el traductor escribe la cabecera en la F47011 y las líneas en la F47012; el R47011 lee esas tablas, las valida y crea el pedido de venta en las F4201 y F4211. [18] Como las F47 son un área de espera, los datos se pueden inspeccionar y corregir antes de que se conviertan en un pedido real. En la salida, el R47042 extrae las facturas a las tablas de salida (F47046 y F47047), que el traductor convierte en 810.

El EDI es adecuado para el intercambio de documentos estandarizados con clientes y proveedores, normalmente junto con un traductor EDI y un canal de comunicación (VAN o AS2).

Explicación conceptual y técnica

Los conectores legados comprenden: [16] [15]

  • XML CallObject, XMLList, XMLTrans y XML Dispatch: documentos XML enviados al Enterprise Server para llamar a business functions, leer listas o escribir transacciones.
  • Dynamic Java Connector: aplicaciones Java llaman a business functions de forma dinámica, con bibliotecas de JDE del lado del cliente.
  • COM Connector: integración con Visual Basic y VC++ mediante el modelo COM de Microsoft.
  • XPI: integración con generaciones anteriores de Oracle Fusion Middleware.

Todavía existen en los entornos antiguos, pero no se recomiendan para los proyectos nuevos: atan el cliente al protocolo interno JDENET y a las bibliotecas de un Tools Release específico, carecen de los mecanismos de seguridad actuales y son difíciles de monitorear.

En una frase: leer directamente de la base de datos es aceptable para informes; escribir directamente en ella es buscarse datos incoherentes.

Explicación conceptual y técnica

Escribir directamente en la base de datos es técnicamente posible, pero no se recomienda. Un INSERT o un UPDATE se salta todo lo que hace la aplicación: validaciones contra el diccionario de datos y las UDC, next numbers (F0002), tablas relacionadas (compromisos de inventario en la F41021, saldos contables en la F0902), campos de auditoría (usuario, programa, fecha y hora), workflow y seguridad de JDE. El resultado típico son saldos que no cuadran, números duplicados y registros huérfanos. La excepción es la propia tabla Z, diseñada para recibir datos desde fuera.

En lectura (informes, BI, vistas) es aceptable, siempre que se respeten las convenciones de JDE:

  • Fechas julianas en el formato CYYDDD: 126271 es el día 271 de 2026, el 28/09/2026.
  • Decimales implícitos: los valores se guardan como enteros, con los decimales definidos en el diccionario de datos o por la moneda. [25]
  • UDC: los códigos hay que traducirlos mediante la F0005.
  • Campos alineados: la unidad de negocio (MCU) tiene 12 posiciones alineadas a la derecha.
  • La seguridad por fila y por columna de JDE no se aplica a quien lee la base de datos.

Seguridad en todas las opciones

  • Identidad: un usuario de servicio por integración, sin acceso interactivo y con rol mínimo en el Security Workbench; credenciales en un vault, nunca en scripts o XML. [27]
  • Transporte: TLS en todas partes (AIS, BSSV, Transaction Server, SFTP, AS2); JDENET queda en la red de los servidores.
  • Perímetro: API gateway o reverse proxy, WAF, límites de solicitudes y lista de orígenes permitidos; servidores de JDE en una zona interna.
  • Datos: el mínimo de datos personales en tablas Z y archivos, purga periódica, cifrado de los archivos en reposo y enmascaramiento en las réplicas, en línea con el RGPD.
  • Auditoría: campos de auditoría de JDE completados con el usuario de la integración, logs correlacionados y registro de quién aprobó cada orquestación.

Gobierno

  • Catálogo de interfaces: responsable de negocio, responsable técnico, método, volumen, SLA y procedimiento de error de cada integración.
  • Cola de errores con un responsable: Work Center, rechazos de los UBE y colas de mensajes no entregados necesitan a alguien que los mire todos los días.
  • Regresión: cada actualización de Tools, ESU o versión puede cambiar una regla; las integraciones forman parte del plan de pruebas.
  • Costo total: además de licencias y servidores, cuenten a las personas que operan y corrigen las interfaces.

Resumen

Para integraciones nuevas y en tiempo real, usen el Orchestrator/AIS. Para grandes volúmenes en batch, las tablas Z con los procesadores estándar son el camino más seguro. Para avisar a los sistemas externos de los eventos, usen los RTE o las notificaciones del Orchestrator.

Para recordar

  • Las reglas de negocio están en las aplicaciones y en las business functions; toda escritura debe pasar por ahí.
  • Orchestrator: una API REST construida en el Studio, con las reglas de las pantallas.
  • Tablas Z: área de espera + procesador estándar; los errores quedan para corregir y reprocesar.
  • BSSV y conectores legados: mantener lo existente y planificar la migración.
  • RTE: JDE avisa; los suscriptores deben ser idempotentes.
  • UBE y EDI: archivos y documentos estandarizados, con transferencia segura.
  • SQL: leer sí, escribir no.

Repaso rápido

1. ¿Cuáles son las tres preguntas que definen el método de integración?

Si es en tiempo real o batch, si JDE envía o recibe los datos y qué Tools Release está en uso.

2. ¿Por qué el Orchestrator respeta las reglas de negocio?

Porque los form requests ejecutan las aplicaciones como un usuario, con las mismas event rules, versiones y opciones de proceso.

3. ¿Qué pasa con un registro de tabla Z que no supera la validación?

Queda en la tabla Z, el mensaje va al Work Center y el registro se puede corregir y reprocesar.

4. ¿Qué opción usar para avisar a un WMS de que un pedido fue liberado?

Los Real-Time Events (o una notificación del Orchestrator), con el WMS suscrito al evento del pedido.

5. ¿Por qué un sistema externo no llama directamente a una business function?

Porque hace falta un contexto de ejecución de JDE, que provee el anfitrión: un UBE, el BSSV o el Orchestrator.

6. ¿Cuándo es aceptable el SQL directo?

Solo para lectura, preferiblemente sobre una réplica y con un usuario de solo lectura, convirtiendo fechas julianas, decimales y UDC.
