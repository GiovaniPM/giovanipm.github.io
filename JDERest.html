Usando REST no JD Edwards

Do conceito à primeira chamada: a infraestrutura, a arquitetura e a configuração do AIS Server, com um exemplo que cria um pedido de compra e consulta o seu status.

Conceito

REST (Representational State Transfer) é um estilo de arquitetura para serviços web: cada recurso tem um endereço (URL), as operações usam os verbos do HTTP (GET, POST, PUT, DELETE) e os dados trafegam em um formato simples, quase sempre JSON. Cada chamada carrega tudo o que o servidor precisa para atendê-la, o que torna as integrações previsíveis e fáceis de testar com ferramentas comuns, como Postman ou curl.

No JD Edwards EnterpriseOne, a porta REST é o AIS Server (Application Interface Services). Ele recebe requisições HTTP com JSON e as traduz em ações sobre o JDE: abrir uma aplicação e preencher um formulário, ler uma tabela ou executar uma orquestração. O ponto central é que o AIS não grava direto no banco: ele executa as mesmas aplicações e business functions que um usuário usaria, com as mesmas versões, opções de processamento e validações. [1] [3]

Sobre o AIS roda o Orchestrator, que permite desenhar, sem código C, uma sequência de passos (regras, form requests, data requests, conectores) e publicá-la como um único endpoint REST. É assim que a Oracle recomenda integrar o JDE hoje. [2]

AIS Server
Servidor Java (em WebLogic ou WebSphere) que expõe o JDE como serviços REST sob o caminho /jderest.
Form request
Chamada que executa um formulário de uma aplicação (por exemplo, P4310_W4310A) como se fosse um usuário.
Data request
Consulta de leitura sobre uma tabela ou business view (por exemplo, F4311).
Orquestração
Sequência de passos publicada como endpoint, com entradas e saídas nomeadas por você.
Orchestrator Studio
Ferramenta web para criar, testar e compartilhar orquestrações.
UDO
User Defined Object: objeto criado por usuários, como orquestrações, com ciclo de aprovação e promoção próprio.

Direções: o JDE pode ser chamado por REST (entrada, pelo AIS) e também chamar APIs REST externas (saída, por conectores do Orchestrator). Este artigo foca na entrada e mostra onde a saída se encaixa.

Infraestrutura necessária

O REST no JDE não é um produto à parte: é uma camada a mais sobre a instalação existente. O mínimo é o seguinte: [1] [5]

ComponentePapelObservação

Enterprise ServerExecuta business functions, MBFs e UBEsJá existe em qualquer instalação.
HTML Server (JAS)Executa as aplicações web que o AIS dirigeRecomenda-se um JAS dedicado ao AIS em produção, para isolar carga.
AIS ServerExpõe os serviços REST em /jderestInstância Java gerenciada pelo Server Manager, em WebLogic ou WebSphere.
Server ManagerInstala, configura e monitora as instânciasConsole central com agentes em cada servidor.
Orchestrator StudioDesenho e teste de orquestraçõesAcessado pelo navegador; nas versões recentes do Tools, integrado ao EnterpriseOne.
Certificados TLSHTTPS de ponta a pontaNunca expor o AIS em HTTP simples fora da rede interna.
API gateway / proxy reversoPonto único de entrada, TLS, WAF, limites de taxaOpcional, mas recomendado sempre que houver consumidores fora da rede.
Usuário de serviçoIdentidade técnica das integraçõesCom o mínimo privilégio, uma role específica e senha gerenciada em cofre.

Dimensionamento: cada sessão do AIS ocupa uma sessão no JAS. Volume alto de chamadas curtas pede um JAS dedicado, reuso de token e um pool de conexões bem ajustado, não apenas mais memória.

Arquitetura

A figura mostra o caminho de uma chamada. Os consumidores (um portal, uma plataforma iPaaS, um aplicativo móvel) falam HTTPS com o API gateway, que encaminha ao AIS Server. O AIS conversa com o HTML Server, que por sua vez usa o protocolo interno JDENET para chegar ao Enterprise Server, onde as business functions acessam o banco. [5]

Três decisões de arquitetura fazem diferença:

  1. Camada de entrada. Colocar um API gateway (OCI API Gateway, Apigee, Kong, Azure APIM ou um proxy reverso) na frente do AIS centraliza TLS, autenticação externa, limites de taxa e registro de acessos, e esconde a topologia interna.
  2. Isolamento. Em produção, o AIS aponta para um HTML Server próprio. Assim, um pico de integrações não deixa lentos os usuários interativos.
  3. Alta disponibilidade. Duas ou mais instâncias de AIS atrás de um balanceador. Como o token amarra a sessão a uma instância, o balanceador precisa de afinidade (sticky session) ou o cliente deve usar orquestrações com autenticação a cada chamada.

Como funciona o REST no JD Edwards

O AIS publica um conjunto de serviços. Os mais usados estão na tabela; a lista completa está na referência da API. [3]

ServiçoEndpointPara quê
TokenPOST /jderest/v2/tokenrequestAutentica e abre uma sessão; devolve o token.
LogoutPOST /jderest/v2/tokenrequest/logoutEncerra a sessão e libera o JAS.
Form servicePOST /jderest/v2/formserviceExecuta um formulário: preenche campos, clica botões, lê a grade.
Data servicePOST /jderest/v2/dataserviceConsulta, conta ou agrega uma tabela ou business view.
App stackPOST /jderest/v2/appstackNavega entre formulários mantendo o estado.
Opções de processamentoPOST /jderest/v2/poserviceLê as opções de processamento de uma versão.
OrquestraçãoPOST /jderest/v3/orchestrator/{nome}Executa uma orquestração publicada.
DescobertaGET /jderest/discoverLista as orquestrações que o usuário pode executar.
ConfiguraçãoGET /jderest/v2/defaultconfigMostra a versão e as capacidades do AIS; ótimo teste de saúde.

O ciclo de uma chamada

Autenticação

  • Token AIS: o cliente chama /v2/tokenrequest com usuário, senha, ambiente e role, e reutiliza o token nas chamadas seguintes: no corpo ("token") para os serviços v2 e no cabeçalho jde-AIS-Auth para o orchestrator v3. É o modelo mais eficiente para muitas chamadas em sequência.
  • HTTP Basic: quando habilitada no AIS, uma orquestração pode ser chamada com Authorization: Basic; o AIS abre e fecha a sessão a cada chamada. É simples e combina com balanceadores sem afinidade, mas custa uma sessão por chamada.
  • OAuth 2.0: nas versões recentes do Tools, o AIS aceita tokens emitidos por um provedor de identidade externo, o que evita guardar a senha do JDE no consumidor. [1]

Respostas e erros

O AIS responde 200 com o JSON do serviço. Os erros mais comuns são 400 (JSON inválido), 403 (sem autorização), 415 (faltou Content-Type: application/json), 444 (token inválido ou expirado) e 500 (erro no processamento, com o corpo trazendo a mensagem e, em orquestrações, o texto de erro do passo). Erros de negócio do JDE, como "fornecedor inválido", vêm no JSON e precisam ser tratados pelo cliente. [4]

Por que preferir orquestrações a chamar o formservice direto? Porque a orquestração dá um contrato estável (entradas com nomes de negócio), esconde os IDs de controle das telas e pode ser alterada sem mexer no consumidor. O formservice direto é ótimo para prototipar e testar. [8]

Como configurar

  1. Pré-requisitos. Confirme o Tools Release, a versão de JDK e de WebLogic suportadas (Certifications no My Oracle Support) e tenha os certificados TLS do host do AIS.
  2. Criar a instância. No Server Manager, use Create/Register a Managed Instance, escolha EnterpriseOne Application Interface Services (AIS) Server, informe o servidor de aplicação, a porta HTTPS e o componente de software do Tools. [1]
  3. Ligar ao HTML Server. Na configuração da instância, aponte para o JAS (de preferência dedicado), defina ambiente e role padrão e confira se o JAS reconhece o AIS (o Server Manager mostra a ligação nos dois lados).
  4. Ajustar a configuração. Revise o timeout de sessão, Allowed Hosts e CORS (para chamadas de navegador), Keep JAS Sessions Open, o tamanho máximo de página de dados e a opção de autenticação Basic, se for usá-la.
  5. Segurança. Crie o usuário de serviço e uma role própria. No Security Workbench (P00950), libere só as aplicações e versões necessárias e a execução das orquestrações (segurança de UDO). Se usar OAuth, configure o provedor de identidade.
  6. Orchestrator Studio. Crie os service requests e as orquestrações, teste no próprio Studio e compartilhe; o administrador aprova e publica. [2]
  7. Testar. Um GET /jderest/v2/defaultconfig responde sem autenticação e mostra a versão do AIS. Depois, peça um token e chame uma orquestração com Postman ou curl. Os logs ficam no Server Manager.
  8. Expor. Publique pelo API gateway, com TLS, limites de taxa, registro de acessos e alertas de disponibilidade.
# teste de saúde (sem autenticação)
GET https://ais.empresa.com:9443/jderest/v2/defaultconfig

# resposta resumida
{ "jasHost": "jas-ais.empresa.local", "aisVersion": "...",
  "capabilityList": [ { "name": "orchestrator" }, { "name": "dataServiceAggregation" }, ... ] }

Checklist antes de produção

  • HTTPS em todos os saltos e certificados com renovação planejada.
  • Usuário de serviço com mínimo privilégio e senha em cofre.
  • JAS dedicado ao AIS e timeouts compatíveis com o consumidor.
  • Orquestrações promovidas como UDOs (DV → PY → PD), nunca recriadas à mão.
  • Monitoração: disponibilidade do defaultconfig, tempo de resposta e taxa de erros.

Exemplo: pedido de compra passo a passo

O cenário: um sistema de compras externo precisa criar pedidos de compra (tipo OP) no JDE e, depois, acompanhar o status de cada linha. Vamos criar duas orquestrações: ORCH_PO_Create e ORCH_PO_Status. [6]

Passo 1. Preparar o JDE

  • Escolha a versão do P4310 (Purchase Orders) que será usada pela integração, por exemplo ZJDE0001 ou uma cópia própria, com as opções de processamento corretas (tipo de pedido OP, aprovação, impressão).
  • Libere essa versão e a execução das duas orquestrações para a role do usuário de serviço.
  • Crie o pedido uma vez à mão, com os mesmos dados que a integração enviará, para confirmar que não há erro de negócio.

Passo 2. Criar o form request no Orchestrator Studio

No Studio, crie um service request do tipo Form Request chamado SR_PO_Create, carregue a aplicação P4310, formulário W4310A (Order Detail), versão ZJDE0001. O Studio lista os campos do cabeçalho e as colunas da grade; marque os que recebem valor e a ordem das ações: [9]

OrdemCampo do formulárioEntrada da orquestração
1Supplier (fornecedor, AN8)Supplier
2Branch/Plant (filial, MCU)BranchPlant
3Reference (VR01)ExternalRef
4Grade: Item Number (LITM)Item
5Grade: Quantity Ordered (UORG)Quantity
6Grade: Unit Cost (PRRC)UnitCost
7Botão OK(ação)

Em Returns, marque o número do pedido (DOCO) e o tipo (DCTO). Se a versão limpar a tela depois do OK, uma alternativa robusta é gravar uma referência externa única no campo Reference e buscar o número do pedido por ela em um data request logo em seguida; essa referência também evita duplicidade quando o cliente repete a chamada.

Várias linhas: para pedidos com N itens, declare a entrada como uma lista (array) e use a opção de repetir as linhas da grade para cada elemento. O exemplo usa uma linha para ficar curto.

Passo 3. Criar a orquestração de criação

Crie a orquestração ORCH_PO_Create, adicione o passo SR_PO_Create, mapeie as entradas e dê nomes de negócio às saídas (OrderNumber, OrderType). Opcionalmente, antes do form request, inclua uma regra que rejeite quantidade ou custo menores ou iguais a zero, para devolver um erro claro sem abrir a aplicação. Teste no Studio e compartilhe para aprovação.

Passo 4. Chamar a criação do pedido

# com autenticação Basic (se habilitada no AIS)
POST https://ais.empresa.com:9443/jderest/v3/orchestrator/ORCH_PO_Create
Authorization: Basic <base64 usuário:senha>
Content-Type: application/json

{ "Supplier": "4343", "BranchPlant": "30", "ExternalRef": "COMPRAS-2026-0917",
  "Item": "1001", "Quantity": "10", "UnitCost": "12.50" }

# resposta 200
{ "OrderNumber": "4450", "OrderType": "OP" }

Se o consumidor fizer muitas chamadas, use o modelo com token: peça o token uma vez e envie-o no cabeçalho jde-AIS-Auth.

# 1. obter o token
POST https://ais.empresa.com:9443/jderest/v2/tokenrequest
{ "username": "SVC_COMPRAS", "password": "********", "deviceName": "compras-int",
  "environment": "JDV920", "role": "INTCOMPRAS" }

# resposta resumida: o token está em userInfo.token
{ "username": "SVC_COMPRAS", "environment": "JDV920",
  "userInfo": { "token": "044Xy...==", ... } }

# 2. chamar a orquestração com o token
POST https://ais.empresa.com:9443/jderest/v3/orchestrator/ORCH_PO_Create
jde-AIS-Auth: 044Xy...==
jde-AIS-Auth-Device: compras-int
Content-Type: application/json

Passo 5. Criar a consulta de status

O status de um pedido de compra fica em cada linha da F4311 (Purchase Order Detail): o último status (LTTR) diz o que já aconteceu e o próximo status (NXTR) diz o que falta. Os códigos seguem as regras de atividade do tipo de pedido (P40204).

No Studio, crie um service request do tipo Data Request chamado SR_PO_Status sobre a tabela F4311, com filtro DOCO = OrderNumber e DCTO = OrderType e retorno de LNID, LITM, UORG, UREC, AOPN, LTTR e NXTR. Coloque-o na orquestração ORCH_PO_Status e nomeie as saídas. Para testar antes de desenhar a orquestração, o mesmo filtro pode ser enviado direto ao data service:

POST https://ais.empresa.com:9443/jderest/v2/dataservice
{ "token": "044Xy...==", "deviceName": "compras-int",
  "targetName": "F4311", "targetType": "table", "dataServiceType": "BROWSE",
  "returnControlIDs": "F4311.DOCO|F4311.DCTO|F4311.LNID|F4311.LITM|F4311.UORG|F4311.UREC|F4311.LTTR|F4311.NXTR",
  "query": { "autoFind": true, "matchType": "MATCH_ALL", "condition": [
    { "controlId": "F4311.DOCO", "operator": "EQUAL", "value": [ { "content": "4450", "specialValueId": "LITERAL" } ] },
    { "controlId": "F4311.DCTO", "operator": "EQUAL", "value": [ { "content": "OP", "specialValueId": "LITERAL" } ] } ] } }

Passo 6. Consultar o status

POST https://ais.empresa.com:9443/jderest/v3/orchestrator/ORCH_PO_Status
jde-AIS-Auth: 044Xy...==
Content-Type: application/json

{ "OrderNumber": "4450", "OrderType": "OP" }

# resposta 200 (saídas nomeadas na orquestração)
{ "Lines": [ { "Line": 1.000, "Item": "1001", "QtyOrdered": 10, "QtyReceived": 0,
               "LastStatus": "280", "NextStatus": "400" } ] }

# ao final do trabalho, encerrar a sessão
POST https://ais.empresa.com:9443/jderest/v2/tokenrequest/logout
{ "token": "044Xy...==" }

A leitura é direta: LastStatus = 280 e NextStatus = 400 significam, neste exemplo, pedido enviado ao fornecedor e aguardando recebimento. O sistema de compras pode consultar periodicamente (polling) ou, melhor, ser avisado: uma notificação do Orchestrator ou um Real-Time Event pode chamar a API do sistema de compras quando o status mudar.

Passo 7. Tratar erros

  • Erros de negócio (fornecedor inexistente, item sem cadastro na filial) voltam no corpo da resposta; devolva-os ao usuário do sistema de compras sem tentar de novo.
  • Erros técnicos (444, 500, timeout) podem ser repetidos, mas só depois de consultar pela referência externa se o pedido já foi criado; é isso que garante a idempotência.
  • Registre sempre a referência externa, o número do pedido e o tempo de resposta.

Conclusão

O REST transformou a forma de integrar o JD Edwards. Com o AIS Server e o Orchestrator, uma operação que antes exigia Business Services em Java ou tabelas Z e UBEs agendados vira um endpoint JSON, desenhado sem código C e que respeita as regras de negócio porque passa pelas próprias aplicações.

O esforço real está menos na chamada e mais no entorno: infraestrutura isolada e segura, usuário de serviço com o mínimo privilégio, contratos estáveis (orquestrações em vez de IDs de tela), idempotência e monitoração. Com isso resolvido, criar um pedido de compra e acompanhar seu status é questão de duas orquestrações e algumas linhas de JSON.

Para fixar

  • AIS Server é a porta REST do JDE; o Orchestrator publica sequências de passos como endpoints.
  • Form requests gravam pelas aplicações; data requests só leem.
  • Token para muitas chamadas; Basic ou OAuth para chamadas isoladas.
  • O status do pedido de compra está em LTTR e NXTR de cada linha da F4311.
  • Referência externa única evita pedidos duplicados.

Para comparar o REST com as outras formas de integração do JDE, veja também Integração no JD Edwards. [7]

Concept

REST (Representational State Transfer) is an architectural style for web services: each resource has an address (URL), operations use HTTP verbs (GET, POST, PUT, DELETE) and data travels in a simple format, almost always JSON. Each call carries everything the server needs to serve it, which makes integrations predictable and easy to test with common tools such as Postman or curl.

In JD Edwards EnterpriseOne, the REST door is the AIS Server (Application Interface Services). It receives HTTP requests with JSON and translates them into actions on JDE: opening an application and filling in a form, reading a table or running an orchestration. The key point is that AIS does not write directly to the database: it runs the same applications and business functions a user would, with the same versions, processing options and validations. [1] [3]

On top of AIS runs the Orchestrator, which lets you design, without C code, a sequence of steps (rules, form requests, data requests, connectors) and publish it as a single REST endpoint. This is how Oracle recommends integrating JDE today. [2]

AIS Server
Java server (on WebLogic or WebSphere) that exposes JDE as REST services under the /jderest path.
Form request
Call that runs an application form (for example, P4310_W4310A) as if it were a user.
Data request
Read query over a table or business view (for example, F4311).
Orchestration
Sequence of steps published as an endpoint, with inputs and outputs named by you.
Orchestrator Studio
Web tool to create, test and share orchestrations.
UDO
User Defined Object: an object created by users, such as orchestrations, with its own approval and promotion cycle.

Directions: JDE can be called over REST (inbound, through AIS) and can also call external REST APIs (outbound, through Orchestrator connectors). This article focuses on inbound and shows where outbound fits.

Required infrastructure

REST in JDE is not a separate product: it is one more layer on top of the existing installation. The minimum is: [1] [5]

Sizing: each AIS session takes a session on the JAS. A high volume of short calls calls for a dedicated JAS, token reuse and a well-tuned connection pool, not just more memory.

Architecture

The figure shows the path of a call. Consumers (a portal, an iPaaS platform, a mobile app) talk HTTPS to the API gateway, which forwards to the AIS Server. AIS talks to the HTML Server, which in turn uses the internal JDENET protocol to reach the Enterprise Server, where business functions access the database. [5]

Three architecture decisions make a difference:

  1. Entry layer. Putting an API gateway (OCI API Gateway, Apigee, Kong, Azure APIM or a reverse proxy) in front of AIS centralizes TLS, external authentication, rate limits and access logging, and hides the internal topology.
  2. Isolation. In production, AIS points to its own HTML Server. That way, a spike in integrations does not slow down interactive users.
  3. High availability. Two or more AIS instances behind a load balancer. Since the token binds the session to an instance, the balancer needs affinity (sticky sessions), or the client should use orchestrations authenticated on every call.

How REST works in JD Edwards

AIS publishes a set of services. The most used ones are in the table; the full list is in the API reference. [3]

The life cycle of a call

Authentication

  • AIS token: the client calls /v2/tokenrequest with user, password, environment and role, and reuses the token in the following calls: in the body ("token") for v2 services and in the jde-AIS-Auth header for orchestrator v3. It is the most efficient model for many calls in sequence.
  • HTTP Basic: when enabled in AIS, an orchestration can be called with Authorization: Basic; AIS opens and closes the session on each call. It is simple and works with balancers without affinity, but costs one session per call.
  • OAuth 2.0: in recent Tools releases, AIS accepts tokens issued by an external identity provider, which avoids storing the JDE password in the consumer. [1]

Responses and errors

AIS answers 200 with the service JSON. The most common errors are 400 (invalid JSON), 403 (not authorized), 415 (missing Content-Type: application/json), 444 (invalid or expired token) and 500 (processing error, with the body carrying the message and, for orchestrations, the step error text). JDE business errors, such as "invalid supplier", come in the JSON and must be handled by the client. [4]

Why prefer orchestrations over calling formservice directly? Because the orchestration gives a stable contract (inputs with business names), hides the screen control IDs and can be changed without touching the consumer. Calling formservice directly is great for prototyping and testing. [8]

How to configure

  1. Prerequisites. Confirm the Tools Release and the supported JDK and WebLogic versions (Certifications on My Oracle Support), and have the TLS certificates for the AIS host.
  2. Create the instance. In Server Manager, use Create/Register a Managed Instance, choose EnterpriseOne Application Interface Services (AIS) Server, and provide the application server, the HTTPS port and the Tools software component. [1]
  3. Connect to the HTML Server. In the instance configuration, point to the JAS (preferably dedicated), set the default environment and role, and check that the JAS recognizes AIS (Server Manager shows the link on both sides).
  4. Tune the configuration. Review session timeout, Allowed Hosts and CORS (for browser calls), Keep JAS Sessions Open, the maximum data page size and the Basic authentication option, if you are going to use it.
  5. Security. Create the service user and a dedicated role. In Security Workbench (P00950), grant only the required applications and versions and the right to run the orchestrations (UDO security). If you use OAuth, configure the identity provider.
  6. Orchestrator Studio. Create the service requests and orchestrations, test them in the Studio itself and share them; the administrator approves and publishes. [2]
  7. Test. A GET /jderest/v2/defaultconfig answers without authentication and shows the AIS version. Then request a token and call an orchestration with Postman or curl. Logs are in Server Manager.
  8. Expose. Publish through the API gateway, with TLS, rate limits, access logging and availability alerts.
# health check (no authentication)
GET https://ais.company.com:9443/jderest/v2/defaultconfig

# abridged response
{ "jasHost": "jas-ais.company.local", "aisVersion": "...",
  "capabilityList": [ { "name": "orchestrator" }, { "name": "dataServiceAggregation" }, ... ] }

Checklist before production

  • HTTPS on every hop and certificates with planned renewal.
  • Least-privilege service user with the password in a vault.
  • JAS dedicated to AIS and timeouts compatible with the consumer.
  • Orchestrations promoted as UDOs (DV → PY → PD), never rebuilt by hand.
  • Monitoring: defaultconfig availability, response time and error rate.

Example: purchase order step by step

The scenario: an external purchasing system needs to create purchase orders (type OP) in JDE and then follow the status of each line. We will create two orchestrations: ORCH_PO_Create and ORCH_PO_Status. [6]

Step 1. Prepare JDE

  • Choose the version of P4310 (Purchase Orders) the integration will use, for example ZJDE0001 or your own copy, with the right processing options (order type OP, approval, printing).
  • Grant that version and the right to run both orchestrations to the service user's role.
  • Create the order once by hand, with the same data the integration will send, to confirm there are no business errors.

Step 2. Create the form request in Orchestrator Studio

In the Studio, create a service request of type Form Request named SR_PO_Create, load application P4310, form W4310A (Order Detail), version ZJDE0001. The Studio lists the header fields and grid columns; mark the ones that receive a value and the order of the actions: [9]

OrderForm fieldOrchestration input
1Supplier (AN8)Supplier
2Branch/Plant (MCU)BranchPlant
3Reference (VR01)ExternalRef
4Grid: Item Number (LITM)Item
5Grid: Quantity Ordered (UORG)Quantity
6Grid: Unit Cost (PRRC)UnitCost
7OK button(action)

Under Returns, mark the order number (DOCO) and type (DCTO). If the version clears the screen after OK, a robust alternative is to write a unique external reference in the Reference field and look up the order number by it in a data request right afterwards; that reference also prevents duplicates when the client repeats the call.

Multiple lines: for orders with N items, declare the input as a list (array) and use the option to repeat the grid rows for each element. The example uses one line to keep it short.

Step 3. Create the creation orchestration

Create the ORCH_PO_Create orchestration, add the SR_PO_Create step, map the inputs and give business names to the outputs (OrderNumber, OrderType). Optionally, before the form request, add a rule that rejects quantity or cost less than or equal to zero, to return a clear error without opening the application. Test in the Studio and share it for approval.

Step 4. Call order creation

# with Basic authentication (if enabled in AIS)
POST https://ais.company.com:9443/jderest/v3/orchestrator/ORCH_PO_Create
Authorization: Basic <base64 user:password>
Content-Type: application/json

{ "Supplier": "4343", "BranchPlant": "30", "ExternalRef": "PURCH-2026-0917",
  "Item": "1001", "Quantity": "10", "UnitCost": "12.50" }

# 200 response
{ "OrderNumber": "4450", "OrderType": "OP" }

If the consumer makes many calls, use the token model: request the token once and send it in the jde-AIS-Auth header.

# 1. get the token
POST https://ais.company.com:9443/jderest/v2/tokenrequest
{ "username": "SVC_PURCH", "password": "********", "deviceName": "purch-int",
  "environment": "JDV920", "role": "INTPURCH" }

# abridged response: the token is in userInfo.token
{ "username": "SVC_PURCH", "environment": "JDV920",
  "userInfo": { "token": "044Xy...==", ... } }

# 2. call the orchestration with the token
POST https://ais.company.com:9443/jderest/v3/orchestrator/ORCH_PO_Create
jde-AIS-Auth: 044Xy...==
jde-AIS-Auth-Device: purch-int
Content-Type: application/json

Step 5. Create the status query

The status of a purchase order lives on each line of F4311 (Purchase Order Detail): the last status (LTTR) tells what has already happened and the next status (NXTR) tells what is pending. The codes follow the order type's activity rules (P40204).

In the Studio, create a service request of type Data Request named SR_PO_Status over table F4311, filtering DOCO = OrderNumber and DCTO = OrderType and returning LNID, LITM, UORG, UREC, AOPN, LTTR and NXTR. Put it in the ORCH_PO_Status orchestration and name the outputs. To test before designing the orchestration, the same filter can be sent straight to the data service:

POST https://ais.company.com:9443/jderest/v2/dataservice
{ "token": "044Xy...==", "deviceName": "purch-int",
  "targetName": "F4311", "targetType": "table", "dataServiceType": "BROWSE",
  "returnControlIDs": "F4311.DOCO|F4311.DCTO|F4311.LNID|F4311.LITM|F4311.UORG|F4311.UREC|F4311.LTTR|F4311.NXTR",
  "query": { "autoFind": true, "matchType": "MATCH_ALL", "condition": [
    { "controlId": "F4311.DOCO", "operator": "EQUAL", "value": [ { "content": "4450", "specialValueId": "LITERAL" } ] },
    { "controlId": "F4311.DCTO", "operator": "EQUAL", "value": [ { "content": "OP", "specialValueId": "LITERAL" } ] } ] } }

Step 6. Query the status

POST https://ais.company.com:9443/jderest/v3/orchestrator/ORCH_PO_Status
jde-AIS-Auth: 044Xy...==
Content-Type: application/json

{ "OrderNumber": "4450", "OrderType": "OP" }

# 200 response (outputs named in the orchestration)
{ "Lines": [ { "Line": 1.000, "Item": "1001", "QtyOrdered": 10, "QtyReceived": 0,
               "LastStatus": "280", "NextStatus": "400" } ] }

# at the end of the work, close the session
POST https://ais.company.com:9443/jderest/v2/tokenrequest/logout
{ "token": "044Xy...==" }

Reading it is straightforward: LastStatus = 280 and NextStatus = 400 mean, in this example, order sent to the supplier and awaiting receipt. The purchasing system can poll periodically or, better, be notified: an Orchestrator notification or a Real-Time Event can call the purchasing system's API when the status changes.

Step 7. Handle errors

  • Business errors (unknown supplier, item not set up in the branch) come back in the response body; return them to the purchasing user without retrying.
  • Technical errors (444, 500, timeout) can be retried, but only after checking by the external reference whether the order was already created; that is what guarantees idempotency.
  • Always log the external reference, the order number and the response time.

Conclusion

REST has changed the way JD Edwards is integrated. With the AIS Server and the Orchestrator, an operation that once required Java Business Services or Z tables and scheduled UBEs becomes a JSON endpoint, designed without C code and respecting business rules because it goes through the applications themselves.

The real effort lies less in the call and more in what surrounds it: isolated and secure infrastructure, a least-privilege service user, stable contracts (orchestrations instead of screen IDs), idempotency and monitoring. With that in place, creating a purchase order and following its status is a matter of two orchestrations and a few lines of JSON.

Key takeaways

  • The AIS Server is JDE's REST door; the Orchestrator publishes sequences of steps as endpoints.
  • Form requests write through the applications; data requests only read.
  • Token for many calls; Basic or OAuth for isolated calls.
  • Purchase order status is in LTTR and NXTR on each F4311 line.
  • A unique external reference prevents duplicate orders.

To compare REST with JDE's other integration options, see also Integration in JD Edwards. [7]

Concetto

REST (Representational State Transfer) è uno stile architetturale per i servizi web: ogni risorsa ha un indirizzo (URL), le operazioni usano i verbi HTTP (GET, POST, PUT, DELETE) e i dati viaggiano in un formato semplice, quasi sempre JSON. Ogni chiamata porta con sé tutto ciò che serve al server per soddisfarla, e questo rende le integrazioni prevedibili e facili da testare con strumenti comuni come Postman o curl.

In JD Edwards EnterpriseOne, la porta REST è l'AIS Server (Application Interface Services). Riceve richieste HTTP con JSON e le traduce in azioni su JDE: aprire un'applicazione e compilare un form, leggere una tabella o eseguire un'orchestrazione. Il punto centrale è che l'AIS non scrive direttamente nel database: esegue le stesse applicazioni e business function che userebbe un utente, con le stesse versioni, opzioni di elaborazione e convalide. [1] [3]

Sopra l'AIS gira l'Orchestrator, che permette di disegnare, senza codice C, una sequenza di passi (regole, form request, data request, connettori) e di pubblicarla come un unico endpoint REST. È così che Oracle raccomanda oggi di integrare JDE. [2]

AIS Server
Server Java (su WebLogic o WebSphere) che espone JDE come servizi REST sotto il percorso /jderest.
Form request
Chiamata che esegue un form di un'applicazione (per esempio P4310_W4310A) come se fosse un utente.
Data request
Interrogazione in lettura su una tabella o business view (per esempio F4311).
Orchestrazione
Sequenza di passi pubblicata come endpoint, con input e output a cui dai tu il nome.
Orchestrator Studio
Strumento web per creare, testare e condividere orchestrazioni.
UDO
User Defined Object: oggetto creato dagli utenti, come le orchestrazioni, con un proprio ciclo di approvazione e promozione.

Direzioni: JDE può essere chiamato via REST (ingresso, tramite l'AIS) e può anche chiamare API REST esterne (uscita, tramite i connettori dell'Orchestrator). Questo articolo si concentra sull'ingresso e mostra dove si colloca l'uscita.

Infrastruttura necessaria

Il REST in JDE non è un prodotto a parte: è uno strato in più sopra l'installazione esistente. Il minimo è il seguente: [1] [5]

Dimensionamento: ogni sessione AIS occupa una sessione sul JAS. Un alto volume di chiamate brevi richiede un JAS dedicato, il riuso del token e un pool di connessioni ben regolato, non solo più memoria.

Architettura

La figura mostra il percorso di una chiamata. I consumatori (un portale, una piattaforma iPaaS, un'app mobile) parlano HTTPS con l'API gateway, che inoltra all'AIS Server. L'AIS dialoga con l'HTML Server, che a sua volta usa il protocollo interno JDENET per raggiungere l'Enterprise Server, dove le business function accedono al database. [5]

Tre decisioni di architettura fanno la differenza:

  1. Strato di ingresso. Mettere un API gateway (OCI API Gateway, Apigee, Kong, Azure APIM o un reverse proxy) davanti all'AIS centralizza TLS, autenticazione esterna, limiti di traffico e registrazione degli accessi, e nasconde la topologia interna.
  2. Isolamento. In produzione, l'AIS punta a un HTML Server proprio. Così un picco di integrazioni non rallenta gli utenti interattivi.
  3. Alta disponibilità. Due o più istanze AIS dietro un bilanciatore. Poiché il token lega la sessione a un'istanza, il bilanciatore ha bisogno di affinità (sticky session), oppure il client deve usare orchestrazioni autenticate a ogni chiamata.

Come funziona il REST in JD Edwards

L'AIS pubblica un insieme di servizi. I più usati sono nella tabella; l'elenco completo è nel riferimento dell'API. [3]

Il ciclo di una chiamata

Autenticazione

  • Token AIS: il client chiama /v2/tokenrequest con utente, password, ambiente e ruolo, e riusa il token nelle chiamate successive: nel corpo ("token") per i servizi v2 e nell'intestazione jde-AIS-Auth per l'orchestrator v3. È il modello più efficiente per molte chiamate in sequenza.
  • HTTP Basic: se abilitata nell'AIS, un'orchestrazione può essere chiamata con Authorization: Basic; l'AIS apre e chiude la sessione a ogni chiamata. È semplice e funziona con bilanciatori senza affinità, ma costa una sessione per chiamata.
  • OAuth 2.0: nelle versioni recenti del Tools, l'AIS accetta token emessi da un provider di identità esterno, evitando di conservare la password JDE nel consumatore. [1]

Risposte ed errori

L'AIS risponde 200 con il JSON del servizio. Gli errori più comuni sono 400 (JSON non valido), 403 (non autorizzato), 415 (manca Content-Type: application/json), 444 (token non valido o scaduto) e 500 (errore di elaborazione, con il corpo che riporta il messaggio e, nelle orchestrazioni, il testo di errore del passo). Gli errori di business di JDE, come "fornitore non valido", arrivano nel JSON e devono essere gestiti dal client. [4]

Perché preferire le orchestrazioni al formservice diretto? Perché l'orchestrazione offre un contratto stabile (input con nomi di business), nasconde gli ID di controllo delle schermate e può essere modificata senza toccare il consumatore. Il formservice diretto è ottimo per prototipare e testare. [8]

Come configurare

  1. Prerequisiti. Conferma il Tools Release e le versioni di JDK e WebLogic supportate (Certifications su My Oracle Support) e procurati i certificati TLS per l'host dell'AIS.
  2. Creare l'istanza. Nel Server Manager usa Create/Register a Managed Instance, scegli EnterpriseOne Application Interface Services (AIS) Server e indica l'application server, la porta HTTPS e il componente software del Tools. [1]
  3. Collegare all'HTML Server. Nella configurazione dell'istanza punta al JAS (preferibilmente dedicato), imposta ambiente e ruolo predefiniti e verifica che il JAS riconosca l'AIS (il Server Manager mostra il collegamento su entrambi i lati).
  4. Regolare la configurazione. Rivedi il timeout di sessione, Allowed Hosts e CORS (per chiamate dal browser), Keep JAS Sessions Open, la dimensione massima della pagina di dati e l'opzione di autenticazione Basic, se la userai.
  5. Sicurezza. Crea l'utente di servizio e un ruolo dedicato. Nel Security Workbench (P00950) concedi solo le applicazioni e versioni necessarie e l'esecuzione delle orchestrazioni (sicurezza UDO). Se usi OAuth, configura il provider di identità.
  6. Orchestrator Studio. Crea le service request e le orchestrazioni, testale nello Studio stesso e condividile; l'amministratore approva e pubblica. [2]
  7. Testare. Un GET /jderest/v2/defaultconfig risponde senza autenticazione e mostra la versione dell'AIS. Poi chiedi un token e chiama un'orchestrazione con Postman o curl. I log sono nel Server Manager.
  8. Esporre. Pubblica tramite l'API gateway, con TLS, limiti di traffico, registrazione degli accessi e allarmi di disponibilità.

GET https://ais.azienda.it:9443/jderest/v2/defaultconfig

  "capabilityList": [ { "name": "orchestrator" }, { "name": "dataServiceAggregation" }, ... ] }

Checklist prima della produzione

  • HTTPS su ogni tratto e certificati con rinnovo pianificato.
  • Utente di servizio con privilegio minimo e password in un vault.
  • JAS dedicato all'AIS e timeout compatibili con il consumatore.
  • Orchestrazioni promosse come UDO (DV → PY → PD), mai ricreate a mano.
  • Monitoraggio: disponibilità del defaultconfig, tempo di risposta e tasso di errori.

Esempio: ordine di acquisto passo per passo

Lo scenario: un sistema acquisti esterno deve creare ordini di acquisto (tipo OP) in JDE e poi seguire lo stato di ogni riga. Creeremo due orchestrazioni: ORCH_PO_Create e ORCH_PO_Status. [6]

Passo 1. Preparare JDE

  • Scegli la versione del P4310 (Purchase Orders) che userà l'integrazione, per esempio ZJDE0001 o una copia propria, con le opzioni di elaborazione corrette (tipo ordine OP, approvazione, stampa).
  • Concedi quella versione e l'esecuzione delle due orchestrazioni al ruolo dell'utente di servizio.
  • Crea l'ordine una volta a mano, con gli stessi dati che invierà l'integrazione, per confermare che non ci siano errori di business.

Passo 2. Creare la form request nell'Orchestrator Studio

Nello Studio crea una service request di tipo Form Request chiamata SR_PO_Create, carica l'applicazione P4310, form W4310A (Order Detail), versione ZJDE0001. Lo Studio elenca i campi della testata e le colonne della griglia; seleziona quelli che ricevono un valore e l'ordine delle azioni: [9]

OrdineCampo del formInput dell'orchestrazione
1Supplier (fornitore, AN8)Supplier
2Branch/Plant (filiale, MCU)BranchPlant
3Reference (VR01)ExternalRef
4Griglia: Item Number (LITM)Item
5Griglia: Quantity Ordered (UORG)Quantity
6Griglia: Unit Cost (PRRC)UnitCost
7Pulsante OK(azione)

In Returns seleziona il numero d'ordine (DOCO) e il tipo (DCTO). Se la versione svuota la schermata dopo l'OK, un'alternativa robusta è scrivere un riferimento esterno univoco nel campo Reference e cercare il numero d'ordine con esso in una data request subito dopo; quel riferimento evita anche i duplicati quando il client ripete la chiamata.

Più righe: per ordini con N articoli, dichiara l'input come lista (array) e usa l'opzione di ripetere le righe della griglia per ogni elemento. L'esempio usa una riga per restare breve.

Passo 3. Creare l'orchestrazione di creazione

Crea l'orchestrazione ORCH_PO_Create, aggiungi il passo SR_PO_Create, mappa gli input e dai nomi di business agli output (OrderNumber, OrderType). Facoltativamente, prima della form request, includi una regola che rifiuti quantità o costo minori o uguali a zero, per restituire un errore chiaro senza aprire l'applicazione. Testa nello Studio e condividi per l'approvazione.

Passo 4. Chiamare la creazione dell'ordine

# con autenticazione Basic (se abilitata nell'AIS)
POST https://ais.azienda.it:9443/jderest/v3/orchestrator/ORCH_PO_Create
Authorization: Basic <base64 utente:password>
Content-Type: application/json

{ "Supplier": "4343", "BranchPlant": "30", "ExternalRef": "ACQ-2026-0917",
  "Item": "1001", "Quantity": "10", "UnitCost": "12.50" }

# risposta 200
{ "OrderNumber": "4450", "OrderType": "OP" }

Se il consumatore fa molte chiamate, usa il modello con token: richiedi il token una volta e invialo nell'intestazione jde-AIS-Auth.

# 1. ottenere il token
POST https://ais.azienda.it:9443/jderest/v2/tokenrequest
{ "username": "SVC_ACQ", "password": "********", "deviceName": "acq-int",
  "environment": "JDV920", "role": "INTACQ" }

# risposta ridotta: il token è in userInfo.token
{ "username": "SVC_ACQ", "environment": "JDV920",
  "userInfo": { "token": "044Xy...==", ... } }

# 2. chiamare l'orchestrazione con il token
POST https://ais.azienda.it:9443/jderest/v3/orchestrator/ORCH_PO_Create
jde-AIS-Auth: 044Xy...==
jde-AIS-Auth-Device: acq-int
Content-Type: application/json

Passo 5. Creare la consultazione dello stato

Lo stato di un ordine di acquisto si trova su ogni riga della F4311 (Purchase Order Detail): l'ultimo stato (LTTR) dice cosa è già successo e lo stato successivo (NXTR) dice cosa manca. I codici seguono le regole di attività del tipo d'ordine (P40204).

Nello Studio crea una service request di tipo Data Request chiamata SR_PO_Status sulla tabella F4311, con filtro DOCO = OrderNumber e DCTO = OrderType e ritorno di LNID, LITM, UORG, UREC, AOPN, LTTR e NXTR. Inseriscila nell'orchestrazione ORCH_PO_Status e dai un nome agli output. Per testare prima di disegnare l'orchestrazione, lo stesso filtro può essere inviato direttamente al data service:

POST https://ais.azienda.it:9443/jderest/v2/dataservice
{ "token": "044Xy...==", "deviceName": "acq-int",
  "targetName": "F4311", "targetType": "table", "dataServiceType": "BROWSE",
  "returnControlIDs": "F4311.DOCO|F4311.DCTO|F4311.LNID|F4311.LITM|F4311.UORG|F4311.UREC|F4311.LTTR|F4311.NXTR",
  "query": { "autoFind": true, "matchType": "MATCH_ALL", "condition": [
    { "controlId": "F4311.DOCO", "operator": "EQUAL", "value": [ { "content": "4450", "specialValueId": "LITERAL" } ] },
    { "controlId": "F4311.DCTO", "operator": "EQUAL", "value": [ { "content": "OP", "specialValueId": "LITERAL" } ] } ] } }

Passo 6. Consultare lo stato

POST https://ais.azienda.it:9443/jderest/v3/orchestrator/ORCH_PO_Status
jde-AIS-Auth: 044Xy...==
Content-Type: application/json

{ "OrderNumber": "4450", "OrderType": "OP" }

# risposta 200 (output nominati nell'orchestrazione)
{ "Lines": [ { "Line": 1.000, "Item": "1001", "QtyOrdered": 10, "QtyReceived": 0,
               "LastStatus": "280", "NextStatus": "400" } ] }

# alla fine del lavoro, chiudere la sessione
POST https://ais.azienda.it:9443/jderest/v2/tokenrequest/logout
{ "token": "044Xy...==" }

La lettura è diretta: LastStatus = 280 e NextStatus = 400 significano, in questo esempio, ordine inviato al fornitore e in attesa di ricevimento. Il sistema acquisti può interrogare periodicamente (polling) o, meglio, essere avvisato: una notifica dell'Orchestrator o un Real-Time Event può chiamare l'API del sistema acquisti quando lo stato cambia.

Passo 7. Gestire gli errori

  • Errori di business (fornitore inesistente, articolo non configurato nella filiale) tornano nel corpo della risposta; restituiscili all'utente del sistema acquisti senza ritentare.
  • Errori tecnici (444, 500, timeout) si possono ritentare, ma solo dopo aver verificato con il riferimento esterno se l'ordine è già stato creato; è questo che garantisce l'idempotenza.
  • Registra sempre il riferimento esterno, il numero d'ordine e il tempo di risposta.

Conclusione

Il REST ha cambiato il modo di integrare JD Edwards. Con l'AIS Server e l'Orchestrator, un'operazione che prima richiedeva Business Services in Java o tabelle Z e UBE schedulati diventa un endpoint JSON, disegnato senza codice C e rispettoso delle regole di business perché passa per le applicazioni stesse.

Lo sforzo vero sta meno nella chiamata e più in ciò che la circonda: infrastruttura isolata e sicura, utente di servizio con privilegio minimo, contratti stabili (orchestrazioni invece di ID di schermata), idempotenza e monitoraggio. Risolto questo, creare un ordine di acquisto e seguirne lo stato è questione di due orchestrazioni e poche righe di JSON.

Da ricordare

  • L'AIS Server è la porta REST di JDE; l'Orchestrator pubblica sequenze di passi come endpoint.
  • Le form request scrivono tramite le applicazioni; le data request leggono soltanto.
  • Token per molte chiamate; Basic o OAuth per chiamate isolate.
  • Lo stato dell'ordine di acquisto è in LTTR e NXTR di ogni riga della F4311.
  • Un riferimento esterno univoco evita ordini duplicati.

Per confrontare il REST con le altre forme di integrazione di JDE, vedi anche L'integrazione in JD Edwards. [7]
